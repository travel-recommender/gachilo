## 2. 150곳 데이터 — 엔진에 그대로는 못 넣습니다

`osaka_places_150_fresh.json`(schema_version 2, `draft_for_review`)의 150곳을 엔진 `Place` 타입과 대조했습니다.

### 2.1 필드 이름·형식이 다릅니다

| 150곳 데이터 | 엔진 `Place` | 비고 |
| --- | --- | --- |
| `place_id` | `id` | 이름만 다름 |
| `name` / `name_ko` | `name` | 어느 쪽을 화면에 쓸지 결정 필요 |
| `category` = `"명소"` | `category` = `"landmark"` | 한글 라벨 ↔ 영문 id 매핑 필요 |
| `opening_hours` = 자유 문장 | `openFrom` / `openTo` = 분 단위 정수 | **파싱 필요** |
| `area` = `"大阪市中央区"` | `area` = `"난바"` | 아래 2.3 |
| 없음 | `popularity` | **아래 2.4 — 우리 파트에 직접 영향** |
| 없음 | `exposure` | 날씨 반영(10주차)에 쓰일 값 |

### 2.2 빈칸 현황 (150곳, 2026-09-30 기준)

`stay_min` · `bag_load` · `name_ko` 는 그 사이 전부 채워졌습니다. 남은 것은 아래입니다.

| 필드 | 빈값 | 엔진에서 하는 일 |
| --- | --- | --- |
| `cost` | 116곳 | 예산 제약 전체가 이 값으로 돌아감 |
| `covered` | 116곳 | 10주차 날씨 반영 |
| `opening_hours` | 18곳 | 영업시간 배치 |
| `address` | 2곳 | 화면 표시 |

`cost` 116곳은 "무료라서 0"과 "아직 확인 못 함"이 구분되어야 합니다. null을 0으로 바꾸면
유료 장소가 공짜로 계산되어 예산 합의가 깨집니다(#24 노트에도 같은 내용이 적혀 있습니다).

### 2.3 `area`가 행정구라 동선 묶기가 깨집니다

엔진은 `area`를 "우메다 / 난바 / 베이" 같은 **관광 권역**으로 쓰고, 하루 일정을 이 단위로 묶습니다. AI에 넘기는 근거 JSON의 지역 간 거리표도 같은 값을 씁니다. 150곳의 `area`는 `大阪市中央区` 같은 행정구라, 그대로 넣으면 난바와 신사이바시가 한 덩어리가 되고 묶는 의미가 사라집니다.

좌표는 전부 있으니 권역은 좌표로 다시 매길 수 있습니다. 행정구 필드는 남겨두고 `area`만 따로 두는 쪽을 제안합니다.

### 2.4 `popularity`가 없으면 AI 추천이 무너집니다 — 우리 쪽 문제

`consensus.ts:175`의 개인 효용 계산입니다.

```
0.08 + 0.42 × (내 카테고리 취향) + 0.38 × place.popularity
```

직접 고르지 않은 장소의 점수 중 **약 절반이 `popularity`에서 나옵니다.** 값이 없으면(`undefined`) 전부 `NaN`이 되고, "아무도 안 골랐지만 모두에게 무난한 곳"을 찾는 AI 후보 선정이 통째로 죽습니다.

`types.ts` 주석에는 "실제 구현에서는 리뷰 수·평점으로 산출한다"고 되어 있는데, 150곳 수집은 OSM 기반이라 리뷰 수가 없습니다. 두 가지 중 하나가 필요합니다.

1. 카테고리별 기본값 하나로 고정 (가장 싸고, 대신 후보 간 변별력이 사라짐)
2. `google_place_links.json`이 이미 있으니 거기서 리뷰 수·평점을 받아 0~1로 정규화

어느 쪽이든 **없는 필드를 0으로 두면 안 됩니다.** 0이면 모든 미선택 장소의 점수가 똑같이 낮아져 AI가 아무것도 못 고릅니다. 결정만 해주시면 우리 쪽에서 대체값 처리를 넣겠습니다.

### 2.5 비용 단위 — 이미 정리되고 있습니다

`docs/week5_data_api_notes.md` 기준으로 JPY 원본 보존 + API 경계에서 KRW 변환 방향이 정해졌고,
`GET /api/places` 의 `exchange_rate` 에 기준일·출처 필드도 추가됐습니다. 엔진과 서버는 원(KRW)
기준이라 이 방향이면 그대로 맞습니다.

남은 것은 실제 환율 숫자와 기준일의 팀 합의입니다. 시연 중에 값이 흔들리지 않도록
**기준일을 고정해 두는 쪽**을 제안합니다.

## 3. 결과 형식

#22가 현재 v0(구현된 것)와 목표 v1을 분리해 두어서, 앞서 "계약과 구현이 전부 다르다"고 쓴
부분은 더 이상 맞지 않습니다. 아래로 갱신합니다.

이번 AI 연결은 **v0 형태에 맞췄습니다.** 설명 문장을 `summary` 에, AI가 추가한 장소를
`days[].placeIds` 에 넣어서 `save_result` 의 키 3개 검증을 건드리지 않았습니다.

v1으로 확장할 때 AI 쪽에서 채울 수 있는 필드는 이렇습니다.

- `explanation` — 지금의 `summary` 그대로
- `alternatives` — "예산을 올리면 무엇이 들어오는지". 규칙으로 계산 가능합니다
- `budget_check` / `stamina_check` — 규칙 엔진이 이미 계산하는 값이라 꺼내 쓰면 됩니다
- `core[].must_of_anonymous` — `Selection.mustOf` 에 memberId가 들어 있으므로 응답에서는
  불리언으로 바꿔야 합니다 (누구의 '꼭'인지 노출 금지)

`alternatives` 를 몇 개까지 낼지만 정해 주시면 맞추겠습니다.
