## 1. 엔진 복사본 — 최신이 맞습니다

`backend/README.md`의 "팀원의 새 알고리즘이 있는지는 별도 확인이 필요합니다"에 대한 답입니다.

`source_manifest.json`의 sha256 4개를 `web/src/lib/`의 현재 파일과 대조했고, 전부 일치합니다. import 확장자를 뺀 본문도 바이트 단위로 동일합니다.

**현재 별도로 반영해야 할 새 알고리즘은 없습니다.** 다만 복사본이라 앞으로 `web/src/lib/`가 바뀌면 조용히 어긋납니다. 계산 요청 때 해시를 비교해 다르면 경고를 남기는 정도를 6주차에 넣어두면 좋겠습니다.

## 2. 150곳 데이터 — 엔진에 그대로는 못 넣습니다

`osaka_places_150_fresh.json`(schema_version 2, `draft_for_review`)의 150곳을 엔진 `Place` 타입과 대조했습니다.

### 2.1 필드 이름·형식이 다릅니다

| 150곳 데이터 | 엔진 `Place` | 비고 |
| --- | --- | --- |
| `place_id` | `id` | 이름만 다름 |
| `name` / `name_ko` | `name` | 어느 쪽을 화면에 쓸지 결정 필요 |
| `category` = `"명소"` | `category` = `"landmark"` | 한글 라벨 ↔ 영문 id 매핑 필요 |
| `opening_hours` = 자유 문장 | `openFrom` / `openTo` = 분 단위 정수 | **파싱 필요** |
| `area` = `"大阪市中央区"` | `area` = `"난바"` | 아래 2.3 |
| 없음 | `popularity` | **아래 2.4 — 우리 파트에 직접 영향** |
| 없음 | `exposure` | 날씨 반영(10주차)에 쓰일 값 |

### 2.2 빈칸 현황 (150곳 기준)

| 필드 | 빈값 | 엔진에서 하는 일 |
| --- | --- | --- |
| `cost` | 127곳 | 예산 제약 전체가 이 값으로 돌아감 |
| `stay_min` | 147곳 | 하루 활동 시간 제약, 시간 배치 |
| `bag_load` | 150곳 | `schedule.ts`의 쇼핑 짐 페널티 |
| `covered` | 127곳 | 10주차 날씨 반영 |
| `address` | 42곳 | 화면 표시 |
| `name_ko` | 110곳 | 화면 표시 |
| `opening_hours` | 26곳 | 영업시간 배치 |

`cost`와 `stay_min`이 비면 **예산·체력 합의가 성립하지 않습니다.** 이슈의 "stay_min·bag_load 규칙 적용(쇼핑 2 / 시장·상점가 1 / 나머지 0, 카테고리 기본 체류시간)"이 그래서 필요한 작업으로 보입니다. 카테고리 기본값으로 채우는 경우, 그 값이 실측이 아니라 추정값이라는 표시를 데이터에 남겨두면 나중에 논문에서 한계로 쓰기 좋습니다.

### 2.3 `area`가 행정구라 동선 묶기가 깨집니다

엔진은 `area`를 "우메다 / 난바 / 베이" 같은 **관광 권역**으로 쓰고, 하루 일정을 이 단위로 묶습니다. AI에 넘기는 근거 JSON의 지역 간 거리표도 같은 값을 씁니다. 150곳의 `area`는 `大阪市中央区` 같은 행정구라, 그대로 넣으면 난바와 신사이바시가 한 덩어리가 되고 묶는 의미가 사라집니다.

좌표는 전부 있으니 권역은 좌표로 다시 매길 수 있습니다. 행정구 필드는 남겨두고 `area`만 따로 두는 쪽을 제안합니다.

### 2.4 `popularity`가 없으면 AI 추천이 무너집니다 — 우리 쪽 문제

`consensus.ts:175`의 개인 효용 계산입니다.

```
0.08 + 0.42 × (내 카테고리 취향) + 0.38 × place.popularity
```

직접 고르지 않은 장소의 점수 중 **약 절반이 `popularity`에서 나옵니다.** 값이 없으면(`undefined`) 전부 `NaN`이 되고, "아무도 안 골랐지만 모두에게 무난한 곳"을 찾는 AI 후보 선정이 통째로 죽습니다.

`types.ts` 주석에는 "실제 구현에서는 리뷰 수·평점으로 산출한다"고 되어 있는데, 150곳 수집은 OSM 기반이라 리뷰 수가 없습니다. 두 가지 중 하나가 필요합니다.

1. 카테고리별 기본값 하나로 고정 (가장 싸고, 대신 후보 간 변별력이 사라짐)
2. `google_place_links.json`이 이미 있으니 거기서 리뷰 수·평점을 받아 0~1로 정규화

어느 쪽이든 **없는 필드를 0으로 두면 안 됩니다.** 0이면 모든 미선택 장소의 점수가 똑같이 낮아져 AI가 아무것도 못 고릅니다. 결정만 해주시면 우리 쪽에서 대체값 처리를 넣겠습니다.

### 2.5 비용 단위

이슈의 "150곳 JPY vs 데모 예산 KRW" 항목입니다. 현재 엔진과 서버는 전부 원(KRW) 기준이고(`budgetPerDay`, `cost`), `docs/API_계약.md`도 "API 경계에서 원화로 환산해 내보낸다"로 적혀 있습니다.

환산을 **어디서 한 번** 할지만 정하면 됩니다. 데이터에 JPY로 두고 서버가 응답할 때 환산하면 환율이 바뀔 때 결과가 달라지므로, **데이터 적재 시점에 원화로 환산해 고정**하고 환율과 기준일을 데이터에 기록하는 쪽을 제안합니다. 시연 중 값이 흔들리지 않는 게 중요합니다.

## 3. 결과 형식 — 문서와 구현이 다릅니다

| | `docs/API_계약.md` | 현재 서버 |
| --- | --- | --- |
| 경로 | `GET /api/rooms/:roomId/result` | `GET /rooms/{roomId}/results` |
| 인증 | 토큰 없음 (링크를 아는 사람이 참여자) | `Authorization: Bearer` 필요 |
| 응답 | `core` / `options` / `excluded` / `schedule` / `explanation` / `alternatives` / `budget_check` / `stamina_check` | `strategy` / `days` / `summary` |
| 날짜 | `day: 1` | `date: "2026-10-01"` |

계약서 쪽이 화면에 필요한 정보를 다 담고 있고, 서버 쪽은 연결 확인용 최소 형태입니다. 둘 중 하나로 맞춰야 혜인님이 화면을 붙일 수 있습니다.

**이번 주 AI 연결은 서버의 현재 형태에 맞췄습니다.** 설명 문장을 `summary`에, AI가 추가한 장소를 `days[].placeIds`에 넣어서, `save_result`의 "키 3개만 허용" 검증을 건드리지 않았습니다.

계약서 형태로 확장할 때 우리 쪽에서 채울 수 있는 필드는 이렇습니다.

- `explanation` — 지금의 `summary` 그대로
- `alternatives` — "예산을 올리면 무엇이 들어오는지". 규칙으로 계산 가능하고, 문장만 AI가 다듬으면 됩니다
- `budget_check` / `stamina_check` — 규칙 엔진이 이미 계산하는 값이라 꺼내 쓰기만 하면 됩니다
- `core[].must_of_anonymous` — 현재 `Selection.mustOf`에 memberId가 들어 있으므로, 응답에서는 불리언으로 바꿔 내보내야 합니다 (누구의 '꼭'인지 노출 금지)

확장을 언제 할지, `alternatives`를 1개만 낼지 3개까지 낼지(계약서 5장 미결)만 정해주시면 맞추겠습니다.
