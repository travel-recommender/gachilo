# 6주차 초대·재접속 연결 초안

기준: [6주차 이슈 #2](https://github.com/travel-recommender/gachilo/issues/2). PR #30의 `8c69bb4`에서 별도 브랜치로 작업했다. #30과 원래 작업 폴더는 변경하지 않는다. 2026-10-03에는 미커밋 공식자료 보완분을 이 브랜치로 복사하여 검사했다. 이 문서는 구현·검사 결과이며 팀의 최종 API 합의를 대신하지 않는다.

## 이번에 구현한 범위

- 개인별 초대 링크 → 해당 참여자의 입력 화면. 방장은 별도 관리 화면에서 현황·계산만 본다.
- 새로고침 → 이 탭의 접속 정보를 읽고 서버에서 **본인이 저장한 입력만** 복원한다. 방장도 관리 화면으로 복원된다.
- 탭을 닫으면 접속 정보가 사라진다. 참여자는 본인 초대 링크, 방장은 생성 직후 보관한 **방장 재접속 링크**로 다시 들어온다.
- 화면이 보이고 온라인일 때 기존 `GET /results`를 약 3초마다 확인한다. 실패하면 최대 30초 간격으로 재시도한다. 동시에 여러 요청을 쌓지 않으며, 오래된 현황 응답이 새 저장·계산 결과를 덮어쓰지 않게 한다.
- 전원 제출 후 방장이 계산하면 같은 저장 결과를 모든 참여자가 확인한다. 입력 변경 시 결과가 무효화되고 전원이 재계산 대기 상태를 본다.
- 기존 데모·실제 수집 장소 모드를 유지한다. 실제 모드는 기존처럼 검토용 초안이며 빈 값을 0으로 바꾸지 않는다.

## 토큰과 비공개 범위

서버의 기존 토큰 발급·해시 저장·Bearer 인증을 사용한다. 새 인증 권한을 추가하지 않는다. 초대는 한 사람당 하나의 입력 토큰이고, 방장 복구 링크는 기존 방장 토큰이다. 링크를 가진 사람은 해당 권한을 갖는다. 링크 회수·만료·계정 기반 복구는 아직 없다.

새 링크는 `/join#room=...&m=...&t=...`, 방장은 `/join#room=...&role=owner&t=...`이다. `#` 뒤의 토큰은 HTTP 요청 경로에 포함되지 않는다. 페이지는 읽은 즉시 주소에서 제거하며 `Referrer-Policy: no-referrer`를 보낸다. 기존 프론트 v2의 `/join/?room=...&m=...&t=...`도 이 확인 화면에서는 읽을 수 있다. Next.js 화면을 자동으로 변경하지 않는다.

활성 접속 정보 하나만 `sessionStorage`에 둔다. 모든 사람의 토큰 목록·개인 입력을 `localStorage`에 넣지 않는다. 방 생성 응답의 참여자 토큰은 링크 표시 후 메모리에만 있으며, 서버는 다시 노출하지 않는다. 따라서 생성 직후 각 링크를 복사해 보관해야 한다. 저장하지 않은 입력 초안은 새로고침 복원 대상이 아니다.

## 혜인님과 검토할 API 연결

기존 요청·응답은 유지한다. 다음 두 GET을 추가했다.

1. `GET /rooms/:roomId` — 방 공용 토큰. 프론트 v2의 `Store.meta` / API 계약 A.6과 같은 `{roomId,startDate,endDate,members:[{id,name}]}`. 실제 모드일 때만 `dataset`을 추가한다. 토큰·선택·개인 조건을 반환하지 않는다.
2. `GET /rooms/:roomId/submissions/:memberId` — **그 참여자의 토큰만**. 기존 PUT과 같은 경로다. `{roomId,memberId,revision,submission}`을 반환하며, 미제출은 `submission:null`이다. 제출했으면 기존 PUT의 필드와 `memberId`를 반환한다. 방장·타인·다른 방·누락 토큰은 403이다.

두 번째 경로는 v0 재접속 확장 초안이다. 계약 B.6의 미래 `/members/:memberId/submission` 경로로 전체 API를 변경한 것이 아니다. 혜인님과 이 경로 및 3초 폴링을 확인한 뒤 Next.js 화면에 연결한다. 기존 서버 확인용 `backend/public`에서만 UI를 구현했다. 별도 프론트 v2 브랜치를 덮어쓰지 않았다.

## 실행과 3대 기기 리허설

Python 3.10+, Node 24+ 필요. 기본은 이 컴퓨터에서만 열리는 로컬 서버다.

```sh
python3 backend/server.py --port 8016
```

같은 Wi-Fi에서 실제 휴대폰으로 시험하려면 실행자가 노트북의 사설 IP를 확인하고 아래 `<노트북_IP>`를 바꾼다. 외부 서비스 배포 설정이 아니다. 허용 출처를 `*`로 열지 않는다.

```sh
python3 backend/server.py --host 0.0.0.0 --port 8016 --origin http://<노트북_IP>:8016
```

1. 노트북에서 `http://<노트북_IP>:8016`으로 접속한다. 휴대폰에서 `127.0.0.1` 링크를 쓰면 안 된다.
2. 초대·재접속 검사에는 데모 36곳 모드로 3명 방을 만든다. 실제 모드는 기존 하나은행 환율 설정이 추가로 필요하다.
3. 방장 복구 링크는 방장만 보관한다. 3명 각자의 초대 링크를 복사해 본인에게 전달한다. 방장도 참여자로 입력할 때는 본인 초대 링크를 새 탭에서 연다.
4. 각자 다른 예산·장소를 저장 → 3/3명 표시 → 각 기기 새로고침 후 자기 값 복원 확인.
5. 방장이 계산 → 세 기기에서 동일 결과 확인. 한 사람 수정 → 이전 결과 사라짐 → 재계산 확인.
6. 네트워크를 끊었다 연결하고 현황이 회복되는지 확인한다. 시험 종료 후 서버를 종료한다.

공개 인터넷 운영 전에는 HTTPS·배포 서버·토큰 만료/재발급 정책을 정해야 한다. 이번 변경은 해당 운영 검토를 완료했다는 뜻이 아니다.

## 완료한 검사와 남은 것

- 백엔드·HTTP **36건 통과**: 세 클라이언트 동시 제출, 서버 재시작 후 본인 값 복원, 공통 결과, 타인·방장·다른 방 토큰 거부, 기존 실제 데이터 계산 포함.
- 세션·폴링 **8건 통과**: 링크 왕복, 방장 복구, 탭별 분리, 잘못된 링크, 재시도/중단, 늦은 응답 무시.
- 기존 일정·안내 회귀검사 **42건**, 공식자료 적용 범위·카테고리 검사 **6건**, 세션·폴링 **8건**을 합친 Node 검사 **56건 통과**. 별도 데이터 검사 **15건**과 백엔드·HTTP **36건**까지 총 **107건 통과** (2026-10-03).
- Chrome 별도 참여자 3탭 + 방장 1탭으로 저장, 새로고침, 자동 참여 현황, 동일 결과를 확인했다. 방장 복구 링크를 새 탭에서 여는 동작도 확인했다.
- **아직 미완료**: 실제 휴대폰 3대·실제 네트워크 단절 리허설, Next.js 사용자 흐름 연결, 팀 API 검토, 약 150곳 일정용 검증, AI 같은 입력 3회 검증.

기능 확인이 끝났더라도 6주차 전체나 GitHub 이슈 완료 체크를 대신하지 않는다.

## 이전 저장 결과의 안내 문구 호환성

[PR #29의 혜인님 의견](https://github.com/travel-recommender/gachilo/pull/29#discussion_r4152719846)에 대한 6주차 후속 보완이다. 해당 의견은 병합을 막지 않는 항목이며, 승인된 PR #30에는 이 변경을 추가하지 않았다.

새로 계산한 실제 장소 결과는 `planning.reason_aggregation: "common_across_dates"`를 포함한다. 이 표시가 있는 결과에만 “모든 여행일 휴무”처럼 날짜 전체에 공통인 사유를 표시한다. 표시가 없거나 다른 값인 저장 결과에는 “이전 계산 결과이거나 집계 기준을 확인할 수 없습니다. 방장이 다시 계산해 주세요.”를 보여준다. 방장이 재계산하면 새 결과와 기준이 함께 저장된다. 읽기만으로 기존 DB의 값이나 집계 기준을 바꾸지 않는다.

표시용 회귀검사 4건과 HTTP 저장·조회·재계산 검사 1건을 추가했다. 기존 150곳 검증 보고서를 다시 생성했으며 집계 기준 필드 하나만 추가됐고 장소·가격·배치 수는 변하지 않았다. 이 필드는 기존 응답에 추가한 호환성 정보이며 팀 API 계약 전체를 새로 확정한 것은 아니다.
