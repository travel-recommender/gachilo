# P3 함께 담기 데이터

Issue #5의 추가 작업 중 **함께 담기 데이터 만들기** 범위다. 기존 P3 저장 API와 SQLite를
이용해 장소별·장소 쌍별 집계 JSON을 만든다. 추천 API, 추천 카드, 자동 추천은 다음 작업이다.

## 어떤 목록을 세는가

- P3(`/pick`)의 **다음**을 눌러 서버 저장에 성공한 목록만 반영된다. 아직 브라우저에만
  있는 클릭·추가·삭제는 집계되지 않는다. `store.tsx`는 `custom_` 장소를 서버 전송에서 제외한다.
- `longlists`에 저장된 P3 목록을 우선한다. 해당 행이 없는 이전 참여자만
  `submissions.payload.longlist`를 사용한다. P4의 `picks`, `must`, 최종 일정은 세지 않는다.
  `longlists` 테이블 자체가 없는 이전 시연 DB도 제출 목록으로 집계하며 원본에 테이블을 만들지 않는다. `rooms.dataset`이 없는 가장 오래된 DB는 데모 모드로 읽고 원본 스키마를 변경하지 않는다.
- `place_selection.saved_longlist`를 P4 pool과 집계가 공통으로 사용한다. P3의 빈 목록 `[]`도 명시적인 저장이므로
  이전 제출 목록으로 되돌리지 않는다. 나중에 제출한 P4 목록과 합쳐서 세지도 않는다.
- **방별 참여자 1명의 현재 목록**이 한 장소 쌍에 최대 1회 기여한다. A와 B의 순서는 무관하다.
  저장 반복·새로고침·재접속은 횟수를 늘리지 않는다. 장소 삭제·목록 비우기·원본 삭제는
  다음 집계에 반영된다. 변경 이력을 누적하는 이벤트 집계가 아니다.
- 서로 다른 참여자가 A만, B만 담았다면 A–B를 함께 담은 사례는 **0회**다.
  방 전체의 합집합인 P4 pool에서 쌍을 만들면 안 된다.
- 저장된 목록의 형식이 잘못되면 집계 CLI는 중단한다. P4 pool은 해당 참여자를 조용히
  제외한 부분 목록 대신 HTTP 503 JSON 안내를 반환한다. 원본 값·참여자 정보는 노출하지
  않으며 DB·입력 revision·기존 결과를 변경하지 않는다. P3에서 정상 목록을 다시 저장하면
  다음 pool 조회부터 복구된다.
- 동일 인물이 여러 방에 참여했는지 식별할 계정이 없다. 따라서 `listCount=3`은
  **“참여 목록 3개에서 함께 담김”**이며 **“고유 사용자 3명”**으로 표시하면 안 된다.

## 실행

저장소 루트에서 Python 3.10 이상으로 실행한다. Node·OSRM·외부 API 호출은 필요 없다.

```bash
python3 backend/co_picks.py \
  --db backend/.local/trips.sqlite3 \
  --output backend/.local/co_pick_counts.json

python3 -m unittest discover -s backend -p 'test_co_picks.py' -v
```

기본 모드는 실제 장소 데이터의 기존 식별자인 `osaka_review_150`이다. 이름의 150은
현재 카탈로그 개수 제한이 아니다. 데모 36곳 집계는 `--dataset prototype_demo_36`으로
별도 실행한다. 두 모드는 절대 섞지 않는다.

서버를 `--db`로 다른 경로에서 실행했다면 **그 파일 경로**를 지정한다. 각 팀원의
노트북 DB는 별개이며 자동으로 합쳐지지 않는다. 시험 방과 실제 이용 방을 구별하는
필드도 아직 없으므로, 실제 이용 통계를 만들 때는 시험용 DB를 섞지 않는다.

기존 테이블에 읽기 전용으로 연결해 하나의 일관된 스냅샷을 읽는다. 별도의 집계 테이블이나
마이그레이션이 없고 서버를 재시작할 필요도 없다. 출력은 **명령을 실행한 시점의 파일**이므로
목록 변경 후 다시 실행해야 한다. 원본 DB가 없거나 형식이 잘못되면 오류로 끝나고
직전 정상 출력은 유지한다. 자료가 없는 정상 DB에서는 쌍이 빈 배열이고 임의 수치는 넣지 않는다.

## 출력 계약 (schemaVersion 1)

| 필드 | 의미 |
| --- | --- |
| `dataset`, `generatedAt` | 집계 대상 모드, 집계 완료 UTC 시각 |
| `countUnit` | `room_member_list` — 방별 참여 목록 단위 |
| `sourcePolicy` | `p3_then_submission_fallback` |
| `savedListCount` | 저장된 목록 수. 명시적인 빈 목록 포함, 미저장 참여자는 제외 |
| `nonEmptyListCount` | 유효 장소가 1개 이상인 목록 수 |
| `pairListCount` | 유효 장소가 2개 이상인 목록 수 |
| `sourceCounts` | P3 저장과 이전 제출 fallback을 사용한 목록 수 |
| `ignoredPlaceSelections` | 현 카탈로그에 없거나 제외·사용자 추가 장소라 걸러진 선택 수 |
| `placeCounts` | `{ placeId, listCount }` — 해당 장소를 담은 목록 수 |
| `minimumListCount` | 기본 3. 이보다 적은 장소·쌍은 내보내지 않음 |
| `pairs` | `{ placeIds: [A, B], listCount }` — 두 장소를 모두 담은 목록 수 |

장소와 쌍은 ID 오름차순으로 저장한다. 같은 쌍은 한 번만 출력하며 셀프 쌍(A–A)은 없다.
이름·방 ID·참여자 ID·토큰·PIN·예산·개인 원본 목록을 직접 내보내지 않는다.
**3개 미만 목록에서 관찰된 장소·쌍은 출력에서 제외**한다. 소표본의 목록 재구성 위험을 줄이기 위한 제한이며, 동일인 다중 방·반복 조회의 차분 추론까지 막는 익명성 보장은 아니다. 집계 파일도 공개 배포하지 않는다. 파일 권한은 교체 전에 명시적으로 0600으로 설정한다.
집계 파일은 기본적으로 gitignore된 `backend/.local/`에 두며 사용자 DB·집계 결과를
저장소에 커밋하지 않는다. 자동 검사에 쓰는 가상 목록을 실제 인기도 수치로 사용하지 않는다.

## 다음 단계에 넘길 기준

- 원본 통계에는 현재 검색 가능한 검증 보류 장소도 포함할 수 있다. 이는 방문 가능성을
  보장하지 않는다. 제거된 ID·`record_status=제외`·`custom_` ID는 집계에서 제외한다.
- 추천 API에서는 **검증 완료 + 방문 날짜의 운영 조건·예산**을 별도로 확인한 후보에만
  이 통계를 적용해야 한다. OSRM 이동 거리·시간, 동행 선택·취향을 함께 고려한다.
- 장소를 선택한 직후 최대 **3곳** 제안, 이미 담은 장소 제외, 사용자가 눌러야 추가.
  추천으로 담은 후보와 **꼭 가기**는 분리한다.
- **“동행도 고른 장소예요”**는 현재 방의 실제 선택을 별도로 확인했을 때만 붙인다.
  전체 방 집계만으로 그 이유나 특정 사람을 추측해서는 안 된다.
- 수치가 적을 때 동선·카테고리 기준으로 제안할 수는 있지만 “함께 담김” 수치를
  만들지 않는다. 최소 3개 목록 기준을 추천 API에도 적용하고 부족하면 지역·카테고리 이유만 표시한다.
