# 사용자 실험 설계 — 10주차

> 이슈 #5 · #17 「실험 설계(윤진)」: 측정 지표 · 설문 문항 · 설명 유/무 비교 조건(H4)
> 참여 동의 · 모집 · 예비 실험 운영은 혜인 담당(#17)이고, 아래 절차를 그대로 쓴다.

---

## 1. 이 실험으로 알고 싶은 것

가설은 4개지만, **사람을 모아서 확인할 수 있는 건 사실상 H4 하나**다.

| 가설 | 어떻게 확인하나 | 이유 |
| --- | --- | --- |
| H1 공정성 전략이 최저 만족도를 올리나 | 시뮬레이션 (가상 그룹 1,000개) | 실험 그룹이 4개뿐이라 그룹끼리 비교하기엔 너무 적다 |
| H2 공정성 전략이 만족도 차이를 줄이나 | 시뮬레이션 | 위와 같음 |
| H3 부분 동행이 만족도를 올리나 | 시뮬레이션 | 위와 같음 |
| **H4 설명을 보여주면 더 잘 받아들이나** | **사용자 실험** | 사람 마음의 문제라 직접 물어봐야 한다 |

그래서 실험의 목적은 두 가지다.

1. **H4 확인하기**
2. **실제 사람들의 만족도 점수 모으기** — 13주에 만족도 계산식을 진짜 데이터에 맞게 고치고(#7), 고친 식으로 H1·H2 시뮬레이션을 다시 돌린다(#8).

## 2. 실험 당일 흐름 (그룹당 약 40분)

| 순서 | 시간 | 하는 일 |
| ---: | ---: | --- |
| 1 | 5분 | 동의서 작성, 사전 질문(4.1) |
| 2 | 15분 | 각자 휴대폰으로 서비스에 들어가 가고 싶은 곳 · 꼭 가기 · 제외 · 예산 · 체력 입력 (여행은 4일로 고정) |
| 3 | 15분 | 서비스가 만든 일정 3개에 **각자** 점수 매기기(4.2). 서로 상의하지 않는다 |
| 4 | 5분 | 순위 · 소감(4.3) |

**참가자에게 안내할 것**
- 가고 싶은 곳은 P3에서 **6곳 이상** 담는다. P4의 꼭 가기는 **0곳부터 선택 가능하며 5곳을 권장**한다 (`optional-must-v1`). 0곳은 건너뛸 수 있고 5곳을 넘겨도 된다.
- 선택한 꼭 가기는 `picks`로, 첫 번째만 `must`(1순위)로 전송한다. 아무것도 고르지 않으면 `picks`는 빈 목록이고 `must`는 없다. 기존 입력·계산 기록은 기존 정책 그대로 보존한다.
- P3에서 장소를 담으면 **추천 카드가 표시되고 추천 API를 호출한다** (`recommendationCards: enabled`). 추천은 선택 사항이며 자동으로 꼭 가기가 되지 않는다. 같은 지역·카테고리 등 대체 추천이 나올 수 있다.
- 일정은 **"일정 A · B · C"**로만 보여준다. 어떤 전략인지 알려주지 않고 표시 순서는 사람마다 섞는다. 실험 중 방장이 일정을 확정하지 않는다.
- 세 일정이 모두 같은 그룹은 전략 비교에서 제외하고 H4와 만족도 점수 분석에만 사용한다.
- 과거 150곳·4인·4일 모의실험의 꼭 가기 3곳 40%, 5곳 62%는 **기존 조건의 기록**이며 0곳 또는 6곳 이상을 허용한 새 조건의 결과가 아니다. 새 세션에서 일정 동일 비율·장소 수를 다시 측정한다(8장).
- 검증된 같은 가게의 대체 지점은 영업·동선과 제외 조건을 확인한 뒤 일정에 배치한다. 지점 자동 배치 뒤 기존 조건(3명·3일·꼭 가기 5곳, 300그룹)의 세 일정이 모두 같은 비율 33~34%는 과거 결과로 기록한다([지점 배치 문서](branch_auto_placement.md)); 새 조건의 추정치로 쓰지 않는다.

### 2.1 추천 카드의 실험 조건과 한계

새 실험에서는 모든 참가자에게 추천 카드를 켠다. 카드의 함께 담긴 횟수는 같은 DB의 다른 방 목록을 기준으로 하며 실제 방문 인원은 아니다. 그룹별 새 DB에는 다른 방 목록이 없으므로 새 실험의 추천은 주로 지역·카테고리 기준으로 표시된다. 추천 카드도 일정 설명과 별도의 정보이므로 H4 해석 시 영향을 고려한다.

같은 DB를 여러 그룹이 사용하면 앞 그룹의 장소 목록이 뒤 그룹의 추천 근거에 영향을 줄 수 있다. 리허설에서 만든 합성 기록도 추천에 노출될 수 있으므로 새 실험은 그룹별 새 DB로 분리하고, 시작 전 리허설 기록이 없는지 확인한다.

기존에 카드를 끄고 꼭 가기를 5곳으로 제한한 세션은 당시 조건의 기록으로 보존한다. 조건이 바뀐 세션을 이전 세션과 섞지 않으며 그룹별 DB 격리·백업·복구는 유지한다.

## 3. 무엇을 재나

### 3.1 컴퓨터가 자동으로 기록하는 것

참가자 한 명 × 일정 하나마다 엔진이 계산해서 저장한다.

- 내 꼭 가기 중 몇 곳이 들어갔나 (찜 반영률)
- 내 1순위 꼭 가기가 들어갔나
- 내가 제외한 곳이 빠졌나
- 내 하루 예산을 몇 % 썼나
- 내 걸음 한도를 몇 % 썼나
- 지금 계산식으로 낸 만족도 점수, 그룹의 평균 · 최저 · 차이

### 3.2 참가자에게 묻는 것 (1~5점)

| 묻는 것 | 문항 | 어디에 쓰나 |
| --- | --- | --- |
| **받아들일 수 있나** | Q1 · Q2 | **H4의 핵심 점수** |
| 만족스럽나 | Q3 | 13주 계산식 보정 |
| 공정한가 | Q4 | H1 · H2 참고 |
| 내 의견이 반영됐나 | Q5 | 참고 |
| 무리인가 | Q6 | 참고 |
| 왜 이렇게 짜였는지 이해되나 | Q7 | 설명이 제대로 전달됐는지 확인 |
| 믿을 수 있나 | Q8 | 참고 |

자동 기록(3.1)과 설문 답(3.2)은 **같은 참가자 번호로 묶어 저장**한다. 그래야 13주에 "어떤 요소가 실제 만족도를 얼마나 좌우하나"를 계산할 수 있다.

## 4. 설문 문항

모든 점수 문항은 1=전혀 아니다 ~ 5=매우 그렇다.

### 4.1 사전 질문 (한 번)

- S1. 최근 3년간 친구·가족과 2인 이상 여행을 몇 번 갔나요? (0 / 1~2 / 3~5 / 6회 이상)
- S2. 그룹 여행을 계획할 때 주로 어떤 역할이었나요? (일정을 도맡음 / 의견을 냄 / 따라감)
- S3. 그룹 여행에서 예산·체력 때문에 말하지 못하고 맞춘 적이 있나요? (1~5점)
- S4. 오사카에 가 본 적이 있나요? (예 / 아니오)

### 4.2 일정마다 (일정 A · B · C 각각)

- Q1. 이 일정대로 여행을 간다면 받아들일 수 있다.
- Q2. 친구들이 이 일정으로 정하자고 하면 동의하겠다.
- Q3. 이 일정에 만족한다.
- Q4. 이 일정은 나를 포함한 모두에게 공정하다.
- Q5. 이 일정에는 내 의견이 반영되어 있다.
- Q6. 이 일정은 나에게 체력이나 예산 면에서 무리다.
- Q7. 이 일정이 왜 이렇게 구성됐는지 이해된다.
- Q8. 이 일정을 만든 방식을 믿을 수 있다.
- Q9. *(설명이 붙은 일정에서만)* 함께 보여준 설명이 일정을 판단하는 데 도움이 됐다.

### 4.3 마지막 (한 번)

- P1. 세 일정을 마음에 드는 순서대로 나열해 주세요. (1~3위)
- P2. 그룹이 하나만 고른다면 어떤 일정이 좋을까요? (A / B / C)
- P3. 이 서비스로 다음 여행을 계획할 의향이 있다. (1~5점)
- P4. 일정을 정하는 데 가장 중요했던 것은? (자유 응답)
- P5. 설명에서 더 알고 싶었던 것이 있다면? (자유 응답)

## 5. H4 — 설명이 있으면 더 잘 받아들이나

### 5.1 핵심 아이디어

> 같은 방의 일정 A·B·C를 한 사람은 모두 설명 없이, 다른 사람들은 모두 설명과 함께 평가한다.

2026-11-17 모의 실험 피드백에 따라 **참가자별 고정 배정**으로 정정했다. 한 사람이 일정마다 두 조건을 번갈아 보지 않는다.

| 참가자 순번 | 일정 A | 일정 B | 일정 C |
| --- | --- | --- | --- |
| 01 | 설명 없음 | 설명 없음 | 설명 없음 |
| 02 | 설명 있음 | 설명 있음 | 설명 있음 |
| 03 | 설명 있음 | 설명 있음 | 설명 있음 |

### 5.2 배정 기준

- 그룹 안에서 같은 일정 글자는 같은 서버 일정이다. 글자와 전략의 대응은 방마다 섞는다.
- 표시 순서는 사람마다 섞되, 설명 조건은 참가자에게 고정한다. 새로고침·재접속·다른 일정 열기로 바뀌지 않는다.
- 01번이 설명 없는 조건이므로 진행자는 참가자 번호를 취향·기대 점수와 무관하게 배정한다. 01번 역할과 설명 조건이 겹치는 한계는 분석에 기록한다.

### 5.3 정책 버전과 과거 기록

- 새 실험 정책은 `participant-fixed-v2`이며 `config/experiment.json`을 화면과 실행기가 함께 읽는다. 4명 이상인 방에서도 01번만 없음, 나머지는 모두 있음이다.
- 서버의 참여자 목록 순서(방 생성 시 번호 순서)를 사용한다. 누가 먼저 접속했는지로 정하지 않는다.
- 기존 `per-candidate-v1`과 정책 필드가 없는 과거 묶음은 당시 일정별 교차 배정으로 내보낸다. 새 정책으로 소급해 다시 이름 붙이지 않는다.
- 시작한 실험 묶음의 정책을 바꿀 수 없다. 새 정책은 새 실험 세션/묶음으로 시작하고, 내보내기에 `explanation_policy`를 남긴다.

### 5.4 설명 있음 vs 없음 — 무엇이 다른가

**설명 문장만 다르고 나머지는 똑같이** 보여준다. 다른 게 섞이면 설명 효과인지 알 수 없기 때문이다.

| 화면에 보이는 것 | 설명 없음 | 설명 있음 |
| --- | :---: | :---: |
| 날짜별 장소 · 시각 · 지도 | O | O |
| 하루 걸음 · 비용 · 이동 거리 | O | O |
| 지점 변경 표시 (고른 곳 · 배치된 지점) | O | O |
| 설명 문장 (지점을 바꾼 이유 포함) | X | O |
| 전략 이름 (평균 · 최소 불만 · 공정성) | X | X |

전략 이름은 **둘 다 숨긴다.** 이름 자체가 일종의 설명이라 조건이 흐려진다.

**설명 문장 예시** — 엔진 결과로 자동으로 채우는 문장 틀이다. AI가 쓰지 않는다(숫자·장소를 지어낼 수 없게).

- 모두에게 같은 설명
  - "1순위를 고른 사람의 꼭 가기가 모두 들어갔어요."
  - "하루 걸음 수는 그룹에서 가장 적은 걸음 한도를 넘지 않아요." (한도 수치는 누구의 값인지 드러날 수 있어 쓰지 않는다)
  - "꼭 가기로 고른 곳 중 2곳은 넣지 못했어요. 주된 이유: 다른 곳을 먼저 넣음, 여행 날짜에 모두 휴무."
- 나에게만 보이는 설명 (다른 사람의 조건은 드러내지 않는다)
  - "내 꼭 가기 5곳 중 4곳이 들어갔어요."
  - "내 1순위 ○○은(는) 같은 가게의 다른 지점인 △△으로 들어갔어요."
  - "빠진 1곳은 화요일 휴무라서예요."
  - "하루 예산의 70%, 걸음 한도의 85%를 써요."
- 지점을 바꾼 일정 칸 (설명 있음에서만)
  - "고른 지점이 그날 운영하지 않아 같은 가게의 영업하는 지점으로 넣었어요."
  - "같은 가게의 앞뒤 장소와 더 가까운 지점으로 바꿔 이동이 약 N분 줄었어요." (N은 엔진 계산값 그대로)
  - "같은 가게의 앞뒤 장소와 더 가까운 지점으로 바꿨어요." (줄어든 분을 계산하지 못한 경우)

**지점 반영 기준.** 꼭 가기·1순위가 들어갔는지는 같은 교체 그룹(`branch_group_id`)의 다른 지점이 들어간 경우도 들어간 것으로 센다. 다른 구성원이 고른 같은 그룹 지점이 들어간 경우도 포함하며, 엔진 `covered`와 같은 기준이다(구현은 #76 `placedEquivalentOf`). 같은 기준을 1순위 반영 확인(낡은 결과 판정)에도 써서, 그룹 공통 문장은 같은 일정을 보는 모든 사람에게 똑같이 보인다. 제외는 정확한 지점 ID로만 본다. 제외한 지점 대신 같은 가게의 다른 지점이 들어가도 "제외한 곳이 들어 있음"으로 보지 않는다(엔진의 제외 의미와 같음).

새 결과의 공통 1순위 문장은 `has_must`와 `must_satisfied`로 모든 참가자에게 동일하게 정한다. 이전에 저장된 결과는 당시 표시를 유지한다.

### 5.5 결과를 어떻게 판단하나

- 현재 배정은 참가자 간 비교다. 한 참가자에게 설명 있음·없음 점수가 모두 존재하는 것을 전제로 한 대응표본 검정은 적용하지 않는다.
- 한 참가자의 A·B·C 평가는 반복 측정이므로 각각을 독립 참가자처럼 세지 않는다. 그룹·참가자 차이를 고려한 분석 방식은 윤진 담당 실험 분석에서 확정한다.
- Q7(이해되나)은 보조 지표로 보고, 수용도(Q1·Q2)와 함께 조건별 점수·차이·불확실성을 보고한다. 높은 점수만으로 설명의 인과 효과가 입증됐다고 말하지 않는다.
- 설명 배정 기록과 실제 열람 여부는 다르다. 현재 내보내기의 `explained`는 표시 조건이며 열람을 증명하지 않는다. 설문 응답은 Google Form에서 별도로 결합한다.
- 과거 교차 배정 실험과 새 참가자 고정 배정의 결과는 정책 버전을 나누어 분석한다. 소규모·비균형 배정(1:2)과 01번 역할이 겹치는 한계를 명시한다.

## 6. 13주와 어떻게 이어지나

참가자 16~20명 × 일정 3개 = 점수 48~60개가 모인다.
"만족스럽나(Q3)" 점수가 자동 기록(찜 반영률 · 1순위 · 제외 · 예산 · 걸음)과 어떻게 연결되는지 계산해서, 지금 임의로 정한 만족도 계산식의 가중치를 실제 값으로 바꾼다(#7). 바꾼 식으로 시뮬레이션을 다시 돌려 H1 · H2를 검정한다(#8).

## 7. 실험 전에 만들어야 하는 것

| 무엇 | 담당(제안) | 내용 |
| --- | --- | --- |
| 실험용 화면 | 혜인 | 일정 A · B · C 표시, 순서 섞기, 전략 이름·확정 버튼 숨기기. 새 실험은 P3 추천 카드를 켜고 P4 꼭 가기를 0곳 이상 자유 선택(5곳 권장)한다(2.1). |
| 설명 켜고 끄기 | 혜인 | 5.3 표대로 01번은 전 일정 설명 없음, 나머지는 전 일정 설명 있음 |
| 설명 문장 만들기 | 윤진 | **완료.** 5.4 문장을 엔진 결과로 자동으로 채우는 기능 (`web/src/lib/experiment.ts`, 문장 목록은 `docs/h4_experiment_screen.md`) |
| 응답 저장 | 조은 | 한 줄 = 참가자 × 일정. `group_id` · `participant_id` · 화면 표시 이름(A/B/C)과 별도로 `candidate_id`(전략) · 입력 `revision` · 표시 순서 · 설명 조건 · 설명 열람 여부 · 설문 답 · 3.1 자동 기록. 순서를 섞어도 자동 기록과 설문을 정확히 묶기 위해서다 |
| 예비 실험 | 혜인 · 윤진 | 1그룹으로 시간, 일정 3개가 다르게 나오는지, 질문이 잘 이해되는지 확인 |

**예비 실험을 시작하기 전에 확인할 것**
- 꼭 가기 0곳·5곳·6곳 이상을 각각 확인한다. 화면 제출 → 저장 → 재접속 복원 → 계산에서 전체 선택이 `picks`, 첫 선택만 `must`이며 0곳이면 빈 `picks`·빈 `must`인지 확인한다(2장 조건).
- 실험 모드에서 설명이 배정표(5.3)대로만 보이고, 전략 이름이 어디에도 안 보이는지 확인한다.
- 실험 방 P3에서 장소를 담은 뒤 추천 카드와 추천 API(`POST /rooms/{roomId}/recommendations/{memberId}`)를 확인한다. 추천을 누르기 전에는 목록에 자동 추가되지 않는지, 새로고침·재접속·뒤로 가기 후에도 입력이 유지되는지 확인한다.
- 그룹마다 별도의 새 DB를 사용하는지, 해당 DB에 리허설용 합성 기록이나 다른 그룹의 목록이 없는지 확인한다.

설문 응답에는 이름 대신 참가자 번호만 쓰고, 예산·체력 원래 값은 분석용 파일에만 남긴다.

## 8. 팀이 정해야 할 것

1. 점수를 5점 척도로 할지 (주제안의 "설명 수용도 5점"과 맞춤)
2. 새 실험의 꼭 가기 0곳 이상 선택·5곳 권장 안내를 확인한다.
3. 7장의 기능을 11주 실험 전(예비 실험 포함)까지 넣을 수 있는지
4. 실험 뒤: 2순위 이후 꼭 가기를 `musts`로 저장할지 (#35 설계는 목록을 받지만 지금 화면·서버는 1곳만 전달). 저장하게 바꾸면 전략이 고를 장소가 줄어 세 후보가 같아지므로, 전략과 꼭 가기의 관계를 같이 정해야 한다
5. (실험 전) 지점 자동 배치·하루 자리 수 변경 뒤 세 일정이 같은 그룹 비율을 `candidate_diversity.mjs`로 다시 재고(2장), 같은 그룹을 전략 비교에서 어떻게 다룰지 정한다

5. 새 조건에서 세 일정의 동일 비율과 하루 장소 수를 다시 측정한다. 이전 결과와 조건 차이를 기록한다.

**새 실험 조건:** P3 추천 카드 사용, P4 꼭 가기는 선택 사항이다(2.1). 이전 실험 기록에는 당시 조건을 유지한다.
