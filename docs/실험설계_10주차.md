> 참여 동의 · 모집 · 예비 실험 운영은 혜인 담당(#17)이고, 아래 절차를 그대로 쓴다.

## 1. 이 실험으로 알고 싶은 것

가설은 4개지만, **사람을 모아서 확인할 수 있는 건 사실상 H4 하나**다.

| 가설 | 어떻게 확인하나 | 이유 |
| --- | --- | --- |
| H1 공정성 전략이 최저 만족도를 올리나 | 시뮬레이션 (가상 그룹 1,000개) | 실험 그룹이 4개뿐이라 그룹끼리 비교하기엔 너무 적다 |
| H2 공정성 전략이 만족도 차이를 줄이나 | 시뮬레이션 | 위와 같음 |
| H3 부분 동행이 만족도를 올리나 | 시뮬레이션 | 위와 같음 |
| **H4 설명을 보여주면 더 잘 받아들이나** | **사용자 실험** | 사람 마음의 문제라 직접 물어봐야 한다 |

그래서 실험의 목적은 두 가지다.

1. **H4 확인하기**
2. **실제 사람들의 만족도 점수 모으기** — 13주에 만족도 계산식을 진짜 데이터에 맞게 고치고(#7), 고친 식으로 H1·H2 시뮬레이션을 다시 돌린다(#8).

## 2. 실험 당일 흐름 (그룹당 약 40분)

| 순서 | 시간 | 하는 일 |
| ---: | ---: | --- |
| 1 | 5분 | 동의서 작성, 사전 질문(4.1) |
| 2 | 15분 | 각자 휴대폰으로 서비스에 들어가 가고 싶은 곳 · 꼭 가기 · 제외 · 예산 · 체력 입력 (여행은 4일로 고정) |
| 3 | 15분 | 서비스가 만든 일정 3개에 **각자** 점수 매기기(4.2). 서로 상의하지 않는다 |
| 4 | 5분 | 순위 · 소감(4.3) |

**참가자에게 안내할 것**
- 가고 싶은 곳은 6곳 이상 담고, **꼭 가기는 5곳**을 고른다.
  - 고르는 곳이 적으면 일정 3개가 똑같이 나온다. 시뮬레이션(실제 150곳, 4명·4일, 200그룹)에서 꼭 가기 3곳이면 40%, 5곳이면 62%만 서로 다르게 나왔다.
  - 그래도 3개가 똑같이 나온 그룹은 전략 비교에서 빼고, H4와 만족도 점수 데이터로만 쓴다.
  - **입력이 엔진에 가는 방식(실험 조건으로 고정):** 지금 서비스는 꼭 가기 5곳을 모두 `picks`로 보내고, 그중 첫 곳만 `must`(1순위)로 보낸다. 위 시뮬레이션도 똑같이 넣었다. 그래서 1순위만 자리 수와 상관없이 먼저 들어가고, 나머지 4곳은 전략이 순서를 정한다.
  - 5곳을 모두 `musts`로 저장하게 바꾸면 꼭 가기가 전략과 상관없이 맨 앞에 서서, 같은 시뮬레이션에서 세 후보가 갈린 그룹이 **0%**가 됐다(꼭 가기 미충족 그룹도 16 → 143/200). 그러면 전략 비교를 할 수 없으므로, **실험 동안은 지금 전달 방식을 유지한다.** 2순위 이후 꼭 가기를 `musts`로 저장할지는 실험 뒤 따로 정한다(8장).
  - **재현:** `node scripts/experiment/candidate_diversity.mjs` (시드 20261026, 그룹 200개, 데이터 `osaka_places_150_fresh.json` sha256 `19f726847da1…`). main `b7201d3`에서 40% · 62% · 0%와 꼭 가기 미충족 16 · 16 · 143이 그대로 나오는 것을 확인했다. 엔진이나 데이터가 바뀌면 다시 돌려서 이 숫자를 고친다.
- 일정은 **"일정 A · B · C"**로만 보여준다. 어떤 전략(평균 · 최소 불만 · 공정성)으로 만들었는지는 알려주지 않는다. 알면 선입견이 생긴다. 순서도 사람마다 섞는다.
- 실험 중에는 방장이 일정을 확정하지 않는다.
- **P3 추천 카드(#61 · #62 · #65)는 실험 동안 보이지 않게 한다.** 참가자는 검색으로만 장소를 담는다.

### 2.1 P3 추천 카드를 끄는 이유

추천 카드의 "N개 참여 목록에서 함께 담김" 숫자는 **같은 서버 DB에 있는 다른 방**의 P3 목록으로 계산된다. 실험을 같은 서버에서 그룹별로 차례로 진행하면 아래 문제가 생긴다.

| 문제 | 왜 문제인가 |
| --- | --- |
| 앞 그룹의 목록이 뒤 그룹 추천에 보인다 | 그룹마다 조건이 달라진다. 뒤 그룹일수록 추천이 많아져 그룹끼리 독립이 아니게 된다 |
| 시연·리허설용 합성 기록이 보일 수 있다 | 참가자가 가짜 근거를 보고 장소를 고른다 |
| 추천 카드도 일종의 "근거 설명"이다 | 설명 유/무로 수용도를 비교하는 H4(5장)와 섞인다 |

**고려했다 버린 안 — 그룹마다 새 DB + 추천 기록:** 그룹마다 합성 기록이 없는 새 DB를 쓰고, 장소를 추천 카드에서 담았는지 직접 검색했는지 기록하는 방법이다. 그룹 간 영향은 막을 수 있지만, 새 DB에서는 다른 방 기록이 없어 어차피 숫자 근거(3개 이상)가 나오지 않고 지역·카테고리 보충만 나온다. 그러면서 출처 기록 기능을 따로 만들어야 하고 H4와 섞이는 문제는 그대로다.

추천 카드의 효과를 보고 싶다면 실험이 끝난 뒤 별도 조건으로 다룬다.

## 3. 무엇을 재나

### 3.1 컴퓨터가 자동으로 기록하는 것

참가자 한 명 × 일정 하나마다 엔진이 계산해서 저장한다.

- 내 꼭 가기 중 몇 곳이 들어갔나 (찜 반영률)
- 내 1순위 꼭 가기가 들어갔나
- 내가 제외한 곳이 빠졌나
- 내 하루 예산을 몇 % 썼나
- 내 걸음 한도를 몇 % 썼나
- 지금 계산식으로 낸 만족도 점수, 그룹의 평균 · 최저 · 차이

### 3.2 참가자에게 묻는 것 (1~5점)

| 묻는 것 | 문항 | 어디에 쓰나 |
| --- | --- | --- |
| **받아들일 수 있나** | Q1 · Q2 | **H4의 핵심 점수** |
| 만족스럽나 | Q3 | 13주 계산식 보정 |
| 공정한가 | Q4 | H1 · H2 참고 |
| 내 의견이 반영됐나 | Q5 | 참고 |
| 무리인가 | Q6 | 참고 |

자동 기록(3.1)과 설문 답(3.2)은 **같은 참가자 번호로 묶어 저장**한다. 그래야 13주에 "어떤 요소가 실제 만족도를 얼마나 좌우하나"를 계산할 수 있다.

## 4. 설문 문항

모든 점수 문항은 1=전혀 아니다 ~ 5=매우 그렇다.

### 4.1 사전 질문 (한 번)

- S1. 최근 3년간 친구·가족과 2인 이상 여행을 몇 번 갔나요? (0 / 1~2 / 3~5 / 6회 이상)
- S2. 그룹 여행을 계획할 때 주로 어떤 역할이었나요? (일정을 도맡음 / 의견을 냄 / 따라감)
- S3. 그룹 여행에서 예산·체력 때문에 말하지 못하고 맞춘 적이 있나요? (1~5점)
- S4. 오사카에 가 본 적이 있나요? (예 / 아니오)

### 4.2 일정마다 (일정 A · B · C 각각)

- Q1. 이 일정대로 여행을 간다면 받아들일 수 있다.
- Q2. 친구들이 이 일정으로 정하자고 하면 동의하겠다.
- Q3. 이 일정에 만족한다.
- Q4. 이 일정은 나를 포함한 모두에게 공정하다.
- Q5. 이 일정에는 내 의견이 반영되어 있다.
- Q6. 이 일정은 나에게 체력이나 예산 면에서 무리다.
- Q7. 이 일정이 왜 이렇게 구성됐는지 이해된다.
- Q8. 이 일정을 만든 방식을 믿을 수 있다.
- Q9. *(설명이 붙은 일정에서만)* 함께 보여준 설명이 일정을 판단하는 데 도움이 됐다.

### 4.3 마지막 (한 번)

- P1. 세 일정을 마음에 드는 순서대로 나열해 주세요. (1~3위)
- P2. 그룹이 하나만 고른다면 어떤 일정이 좋을까요? (A / B / C)
- P3. 이 서비스로 다음 여행을 계획할 의향이 있다. (1~5점)
- P4. 일정을 정하는 데 가장 중요했던 것은? (자유 응답)
- P5. 설명에서 더 알고 싶었던 것이 있다면? (자유 응답)

## 5. H4 — 설명이 있으면 더 잘 받아들이나

### 5.1 핵심 아이디어

> **같은 일정을 어떤 사람은 설명과 함께, 어떤 사람은 설명 없이 보게 해서 점수를 비교한다.**

예를 들어 철수와 영희는 같은 그룹이라 **똑같은 일정 A · B · C**를 받는다.

| | 일정 A | 일정 B | 일정 C |
| --- | --- | --- | --- |
| 철수 | 설명 **있음** | 설명 없음 | 설명 없음 |
| 영희 | 설명 없음 | 설명 **있음** | 설명 **있음** |

같은 일정 A를 철수는 설명과 함께, 영희는 설명 없이 본다.
각자 "설명 있을 때 점수 평균"과 "설명 없을 때 점수 평균"을 비교해서, **설명이 있을 때 점수가 더 높으면 H4가 맞다.**

### 5.2 왜 이렇게 하나

- **같은 일정을 두 번 보여주면?** (설명 없이 보고 → 설명 보고 다시 평가) 점수가 오른 게 설명 때문인지, 그냥 두 번 봐서인지 구분이 안 된다.
- **그룹을 나누면?** (설명 그룹 2개 / 없는 그룹 2개) 그룹 분위기 차이가 섞이고, 조건당 8~10명밖에 안 된다.
- 그래서 **한 사람이 두 조건을 다 겪게** 하고, 어느 일정에 설명을 붙일지는 사람마다 돌린다.

### 5.3 누구에게 어느 일정에 설명을 붙이나

그룹 안에서 참가자 순번대로 아래 표를 돌려 쓴다. 7명째부터는 다시 1번부터.

| 순번 | 설명 있음 | 설명 없음 |
| ---: | --- | --- |
| 1 | A | B, C |
| 2 | B, C | A |
| 3 | B | A, C |
| 4 | A, C | B |
| 5 | C | A, B |
| 6 | A, B | C |

이렇게 하면 모든 사람이 설명 있음과 없음을 둘 다 겪고, 각 일정도 설명 있음/없음으로 거의 같은 횟수만큼 보여진다.

### 5.4 설명 있음 vs 없음 — 무엇이 다른가

**설명 문장만 다르고 나머지는 똑같이** 보여준다. 다른 게 섞이면 설명 효과인지 알 수 없기 때문이다.

| 화면에 보이는 것 | 설명 없음 | 설명 있음 |
| --- | :---: | :---: |
| 날짜별 장소 · 시각 · 지도 | O | O |
| 하루 걸음 · 비용 · 이동 거리 | O | O |
| 설명 문장 | X | O |
| 전략 이름 (평균 · 최소 불만 · 공정성) | X | X |

전략 이름은 **둘 다 숨긴다.** 이름 자체가 일종의 설명이라 조건이 흐려진다.

**설명 문장 예시** — 엔진 결과로 자동으로 채우는 문장 틀이다. AI가 쓰지 않는다(숫자·장소를 지어낼 수 없게).

- 모두에게 같은 설명
  - "모두의 1순위 꼭 가기 3곳이 모두 들어갔어요."
  - "누군가 제외한 곳은 넣지 않았어요."
  - "하루 걸음 수는 그룹에서 가장 적은 한도 8,000보를 넘지 않아요."
  - "2곳은 방문일 휴무·운영시간 때문에 넣지 못했어요."
- 나에게만 보이는 설명 (다른 사람의 조건은 드러내지 않는다)
  - "내 꼭 가기 5곳 중 4곳이 들어갔어요."
  - "빠진 1곳은 화요일 휴무라서예요."
  - "하루 예산의 70%, 걸음 한도의 85%를 써요."

### 5.5 결과를 어떻게 판단하나

- 참가자마다 (설명 있음 점수 평균 − 설명 없음 점수 평균)을 구해서, 이 차이가 0보다 확실히 큰지 통계 검정한다(대응표본 t검정, 안 맞으면 Wilcoxon).
- Q7(이해되나)은 **보조 지표**로 본다. 설명 있음에서 Q7이 더 높으면 "설명이 이해를 도왔다"는 근거가 된다. 차이가 뚜렷하지 않으면 "이 표본에서 이해도 개선을 확인하지 못했다"고만 쓴다. 원래 일정이 이해하기 쉬워 두 조건 모두 높게 나올 수도 있고, 표본이 작아 못 잡았을 수도 있기 때문이다.
- 설명을 실제로 봤는지는 Q7이 아니라 **화면 기록**으로 따로 확인한다(설명이 표시된 일정과 열람 여부를 7장 응답 저장에 남긴다).
- 수용도(Q1·Q2) 결과는 Q7 결과와 관계없이 차이 · 효과크기 · 95% 신뢰구간을 함께 보고한다. p값 하나로 결론을 내리지 않는다.
- **한계:** 참가자가 16~20명이라 설명 효과가 꽤 커야 확인된다(효과크기 dz 0.66~0.75 이상). 효과가 작으면 "유의하지 않음"이 나올 수 있다. 그때도 결과와 효과 크기를 숨기지 않고 그대로 보고한다(#8 원칙).

## 6. 13주와 어떻게 이어지나

참가자 16~20명 × 일정 3개 = 점수 48~60개가 모인다.
"만족스럽나(Q3)" 점수가 자동 기록(찜 반영률 · 1순위 · 제외 · 예산 · 걸음)과 어떻게 연결되는지 계산해서, 지금 임의로 정한 만족도 계산식의 가중치를 실제 값으로 바꾼다(#7). 바꾼 식으로 시뮬레이션을 다시 돌려 H1 · H2를 검정한다(#8).

| 응답 저장 | 조은 | 한 줄 = 참가자 × 일정. `group_id` · `participant_id` · 화면 표시 이름(A/B/C)과 별도로 `candidate_id`(전략) · 입력 `revision` · 표시 순서 · 설명 조건 · 설명 열람 여부 · 설문 답 · 3.1 자동 기록. 순서를 섞어도 자동 기록과 설문을 정확히 묶기 위해서다 |
| 예비 실험 | 혜인 · 윤진 | 1그룹으로 시간, 일정 3개가 다르게 나오는지, 질문이 잘 이해되는지 확인 |

**예비 실험을 시작하기 전에 확인할 것**
- 각자 고른 꼭 가기 5곳이 화면 제출 → 서버 저장 → 본인 입력 복원 → 세 전략 계산까지 `picks` 5곳 · `must` 1곳으로 그대로 가는지 확인한다(2장 조건).
- 실험 모드에서 설명이 배정표(5.3)대로만 보이고, 전략 이름이 어디에도 안 보이는지 확인한다.
- 실험 방의 P3에서 추천 카드가 보이지 않고, 추천 API(`/recommendations`) 요청이 서버 로그에 남지 않는지 확인한다.

설문 응답에는 이름 대신 참가자 번호만 쓰고, 예산·체력 원래 값은 분석용 파일에만 남긴다.
