# P3 함께 담기 추천 API

Issue #5의 추가 작업. 집계 기반은 [P3 함께 담기 데이터](p3_co_pick_data.md)이며, P3 카드에서 근거를 보여 주고 사용자가 누른 곳만 My list에 추가한다. 자동 담기·꼭 가기 지정은 하지 않는다.

## 요청

`POST /rooms/{roomId}/recommendations/{memberId}`

- `Authorization: Bearer <본인 submissionToken>` 필수. 방장도 본인의 참여자 토큰을 사용한다. 공용 초대 토큰·방장 관리 토큰·다른 참여자의 토큰으로 개인 목록을 조회할 수 없다.
- `Content-Type: application/json`. POST는 조회용이며 추천/목록/입력 revision/결과를 저장하거나 변경하지 않는다. 기존 개인 링크 정책대로 미점유 참여자 자리만 사용 중으로 표시할 수 있다.

```json
{
  "placeId": "osaka_001",
  "excludePlaceIds": ["osaka_002"],
  "limit": 3
}
```

| 필드 | 규칙 |
| --- | --- |
| placeId | 기준 장소 ID, 필수. 해당 방 데이터 모드의 알려진 비제외 장소. 아직 P3에 저장하지 않았어도 사용 가능 |
| excludePlaceIds | 선택. 현재 화면에서 이미 담은 장소 ID 최대 30개. 기본 `[]`, 중복은 한 번으로 처리 |
| limit | 선택. 정수 1~10, 기본 3. 문자열·소수·불리언은 거절 |

서버에 저장된 **본인의 P3 목록 + excludePlaceIds + 기준 장소**를 모두 제외한다. P3 저장행이 없는 경우에만 기존 제출의 longlist를 사용하고, 명시적으로 저장한 빈 P3 목록은 빈 목록으로 유지한다. 아직 저장하지 않은 추가 선택은 `excludePlaceIds`에 담아 보낸다. 삭제한 곳을 다시 추천받으려면 먼저 P3 저장 API로 삭제를 반영한다. 다른 동행이 담은 장소는 추천할 수 있다.

## 응답

아래 ID와 숫자는 계약 설명용 예시이며 실제 인기 통계가 아니다.

```json
{
  "dataset": "osaka_review_150",
  "sourcePlaceId": "osaka_001",
  "limit": 3,
  "countUnit": "room_member_list",
  "generatedAt": "2026-11-03T04:00:00+00:00",
  "eligibility": "at_least_one_trip_date",
  "recommendations": [
    {
      "placeId": "osaka_009",
      "name": "오사카성",
      "category": "명소",
      "area": "大阪市中央区",
      "coPickCount": 3,
      "reason": "co_pick"
    }
  ]
}
```

- 각 항목은 현재 카탈로그의 표시 이름·카테고리·지역과 장소 ID를 제공한다. 좌표·가격 등 전체 정보는 `/api/places` 카탈로그와 ID로 연결한다.
- `coPickCount`는 **이 서버 DB의 같은 데이터 모드 중 요청자 방을 제외하고 두 장소를 함께 담은 방별 참여 목록 수**다. 고유 인원 수, 실제 여행 방문 횟수, 현재 동행 수가 아니다. 이름·개인 목록·방/참여자 ID·토큰은 응답하지 않는다.
- 요청 시점마다 집계한다. 반복 저장은 증가시키지 않고 수정·삭제는 다음 요청부터 반영한다. 집계와 본인 제외 목록은 같은 SQLite 읽기 스냅샷을 사용한다. 내보낸 JSON 파일이나 별도 배치 명령이 필요 없다.
- `eligibility=at_least_one_trip_date`: 실제 데이터 중 기존 일정 검증기가 **여행 기간 내 하루 이상** 통과시킨 장소만 반환. 모든 여행일에 열려 있다거나 당일 예약·최종 일정 배치가 보장된다는 뜻은 아니다.
- 36곳 데모 방은 별도 집계·카탈로그를 사용하며 `eligibility=demo_unverified`. 실제 장소 검증을 통과했다고 표시하지 않는다.

## 정렬과 부족한 데이터 처리

1. 검증 통과·미선택 장소 중 함께 담긴 횟수가 3회 이상인 곳을 내림차순 정렬.
2. 부족한 수만 `같은 지역+같은 카테고리 → 같은 지역 → 같은 카테고리` 순으로 채움.
3. 횟수가 같으면 위 지역·카테고리 우선순위, 그다음 장소 ID 오름차순으로 고정.
4. 장소 중복 없음. 조건에 맞는 곳이 부족하면 N개보다 적게 또는 빈 목록 반환. 관계없는 장소로 억지로 채우지 않음.

| reason | 의미 | 화면 문구 예시 |
| --- | --- | --- |
| co_pick | 요청자 방 외의 저장 목록 3개 이상에서 쌍이 관찰됨 | N개 참여 목록에서 함께 담김 |
| same_area_category | 집계가 없어 같은 지역·카테고리로 보충 | 같은 지역 · 같은 카테고리 |
| same_area | 같은 지역으로 보충 | 같은 지역 |
| same_category | 같은 카테고리로 보충 | 같은 카테고리 |

3개 미만의 함께 담기 기록은 순위와 숫자에 사용하지 않고 보충으로 처리하며 `coPickCount`는 0이다. 소표본의 노출 위험을 줄이는 제한이며, 다중 방 생성·외부 지식·시간에 따른 차분 조회까지 막는 익명성 보장은 아니다. 계정 없는 테스트 서비스의 한계로 명시한다. ‘N명이 담았다’, ‘동행도 골랐다’라는 문구로 바꾸면 안 된다. 현재 동행 선택 이유 제공은 후속 단계다.

`place_catalog.area_key`에서 지역 키를 한 번 계산해 서버 시작 시 추천 인덱스에 보관한다. API의 표시용 area 값은 유지한다. 지역은 기존 일본어 구 단위와 신규 지점의 한국어 상권명을 맞추기 위해 **주소/지역에 명시된 오사카시 구를 우선** 사용한다. 그런 주소가 없으면 기존 area의 공백·유니코드만 정규화한다. 지역이 비어 있다고 같은 지역으로 보지 않는다. 구 단위 비교는 가까운 도보 동선을 보장하지 않는다.

## P3 숫자 근거 표시

- 서버 방에서 장소를 담은 직후 기준 장소와 최대 3개 카드를 표시한다. 서버 없는 로컬 모드·직접 만든 장소에는 집계 카드를 만들지 않는다.
- `co_pick`의 3 이상 정수만 **N개 참여 목록에서 함께 담김**으로 표시한다. 지역·카테고리 보충은 숫자를 붙이지 않는다. 집계 단위·기준 장소·데이터 모드·숫자/이유 조합이 잘못된 응답은 오류로 처리한다.
- ‘추천 근거는 어떻게 세나요?’에서 방별 목록 집계, 같은 사람의 다른 방 중복, 시험 데이터 포함 가능성을 설명한다. 현재 동행 수·고유 사람 수·방문 횟수로 표현하지 않는다.
- 실제 장소는 여행 기간 중 하루 이상 가능한 조건이며 날짜별 운영·예약 확인이 필요하다는 안내, 데모는 운영 조건 미검증 안내를 표시한다.
- 담기 버튼은 My list만 바꾼다. picks·must는 그대로이며 ‘다음’에서 저장하는 기존 흐름을 유지한다. 이미 담은 곳·카탈로그에 없는 곳·선택 불가 장소는 카드에서 제외하고 공유된 30곳 한도에서 담기를 막는다. 저장 중 검색·추천 담기·삭제는 비활성화하고 저장 중 안내를 표시한다.
- 기준 장소·참여 토큰/방·데이터 모드 변경 시 이전 요청을 취소하고 지연 응답도 폐기한다. 현재 목록만 바뀌면 같은 추천 묶음을 유지하고 화면에서 걸러내며, 추천으로 담아도 기준 장소를 바꾸지 않는다. 서버에서 최대 6개를 받아 선택 가능·미등록·이미 담음 조건을 거른 뒤 최대 3개만 표시한다. 남은 카드가 없으면 다른 추천 조회 버튼으로 현재 제외 목록을 반영해 새로 받는다. 기준 장소를 빼면 카드가 사라진다. 네트워크/서버 오류는 검색·목록 저장과 분리하며 ‘추천 다시 조회’를 눌러 재시도한다. 요청부터 본문 읽기까지 90초 제한이며 자동 반복하지 않는다.
- 이 API를 지원하는 서버와 같은 버전의 웹이 필요하다. 구버전 서버의 404는 추천 연결 오류로 안내하고 가짜 집계로 대체하지 않는다. PR #60(집계) → #61(API) 위의 화면 변경이며, 기반 PR 병합 후 main 통합 확인이 필요하다.

## 오류 및 적용 범위

- 잘못된 요청/기준 장소 400, 잘못된 본인 토큰 403, 없는 방 404.
- 집계 DB·카탈로그·날짜 검사 실패 또는 요청자 방의 손상 행은 503. 다른 방의 손상 행은 해당 행만 제외하고 제외 개수만 서버 로그에 기록한다(방 ID·원문은 기록하지 않음). 정상 데이터가 없는 경우에만 보충 기준을 적용한다.
- 응답은 `Cache-Control: no-store`. 인증이 성공한 뒤에만 집계/날짜 검사를 실행하며, 날짜 검사 후 토큰을 다시 확인한다.
- 현재 API는 함께 담기·지역·카테고리·여행일 검증까지다. **OSRM 거리 순위, 개인 예산 여유, 동행 이유 문구는 후속 범위**다. 이 API 호출만으로 장소가 자동 일정/꼭 가기에 추가되지 않는다.
- 운영 데이터 파일을 교체했다면 기존 서버 정책대로 재시작한다. 날짜 검증 결과는 서버 프로세스에서 여행 기간별로 캐시된다.
- DB의 현재 목록을 요청마다 읽되, 기준 장소가 들어 있는 목록의 다른 ID만 센다. 모든 장소 쌍 조합을 만들거나 정렬하지 않는다. 카탈로그는 Store 시작 시 이미 읽은 데이터에서 만들고 요청마다 파일을 다시 읽지 않는다. 향후 이용량 증가 시 집계 캐시/갱신 버전을 도입한다. 서로 다른 노트북의 로컬 DB 사이에는 통계가 공유되지 않는다.

## 검증

```sh
python3 -m unittest discover -s backend -p 'test_place_recommendations.py'
python3 -m unittest discover -s backend -p 'test_*.py'
```

Node.js 24 이상 필요. 임시 DB/로컬 HTTP로 정렬·빈 데이터·명시/저장 제외·저장 반복과 삭제·개인 인증·모드 격리·운영일 검증 실패 및 복구를 검사한다. 실제 사용자 인기도·OSRM·물리 다기기 시험은 아니다.
