## 1. 꼭 가기 · 제외 여러 곳 (P4)

### 1.1 우선순위 규칙

개수 제한이 없으므로, 그냥 순서대로 넣으면 **많이 찍은 사람이 자리를 쓸어간다.** 5개 찍은 사람과 1개 찍은 사람이 있으면 후자가 밀린다.

기획서 원리 2는 "모두가 최소 하나는 지킨다"이다. 이걸 목록으로 확장했다.

```
전원의 1순위를 먼저 전부 넣는다
  → 그다음 전원의 2순위를 돈다
    → 그다음 3순위…
```

- **같은 순위 안에서는** 지금까지 지켜진 '꼭'이 적은 사람이 먼저다. 그래도 같으면 memberId 순으로 고정해 같은 입력에 같은 결과가 나오게 한다.
- **1순위는 자리·예산이 모자라도 반드시 코어에 넣는다.** 원리 2를 지키기 위해서다.
- **2순위부터는** 남은 자리와 예산 안에서만 코어로 가고, 못 들어가면 **본인만 가는 옵션**으로 남는다. 아예 버리지 않는다.
- 목록 안의 순서는 본인이 매긴 중요도다(화면에서 고른 순서).

### 1.2 거부와 겹칠 때

남이 거부한 곳은 내 목록에서 빠지고, **다음 순위가 1순위 자리를 이어받는다.** 1순위가 거부당했다고 해서 그 사람이 원리 2의 보장을 잃지는 않는다.

한 사람이 같은 곳을 꼭 가기와 빼기에 동시에 넣으면 입력 오류로 돌려준다.

### 1.3 만족도

`mustKept`(1순위가 지켜졌는가)와 `mustRate`(몇 개나 지켜졌는가)를 나눠서 본다. 점수에서 '꼭' 항목은 **1순위 절반 + 나머지 비율 절반**으로 매긴다. 많이 찍었다고 만족도가 자동으로 낮아지지 않는다.

## 2. 트레이드오프 3축 (P6)

각 0~1. 값이 클수록 오른쪽이고, 어느 쪽도 좋고 나쁨이 아니다.

| 축 | 0 | 1 | 실제로 바뀌는 것 |
| --- | --- | --- | --- |
| `pace` | 여유롭게 | 빡빡하게 | 하루 자리 수 2 → 4곳 |
| `distance` | 이동 짧게 | 멀어도 괜찮게 | 먼 장소 벌점, 배치 순서 |
| `spend` | 아끼기 | 편하게 쓰기 | 예산 상한 70% → 100% |

### 2.1 그룹 값으로 합치는 방법

**축마다 다르게 합친다.** 이게 이번 설계에서 가장 중요한 결정이다.

- `pace` · `distance` → **가장 낮은 값(하한)**. 제약이기 때문이다. 한 명이라도 힘들면 그 사람이 못 따라온다. 기획서 원리 3의 "하한에 맞춘다"와 같다.
- `spend` → **평균**. 취향이기 때문이다. 예산 자체는 이미 하루 예산으로 따로 받아 하한을 쓰고 있어서, 여기서까지 하한을 쓰면 두 번 깎인다.

### 2.2 실제 결과 (3인 3박4일, 같은 장소 입력)

| 설정 | 하루 자리 | 예산 상한 | 코어 | 옵션 |
| --- | ---: | ---: | ---: | ---: |
| 여유·짧은이동·절약 (0.1) | 2곳 | 204,400원 | 8곳 | 3곳 |
| 입력 없음 (0.5) | 3곳 | 238,000원 | 12곳 | 0곳 |
| 빡빡·멀어도OK·넉넉 (0.9) | 4곳 | 271,600원 | 16곳 | 0곳 |

## 3. 날짜별 숙소 (P5)

### 3.1 하루의 시작과 끝

숙소를 받으면 **하루가 숙소에서 시작해 숙소로 끝난다.** 숙소 자체는 방문 장소로 넣지 않고, 이동 거리·시간에만 반영한다. 비용 0원·체류 0분이라 예산과 활동 시간 계산은 그대로다.

`DayPlan`에 세 가지가 추가된다.

```
stayName    그날 숙소 이름
stayOutKm   숙소 → 첫 장소
stayBackKm  마지막 장소 → 숙소
```

`walkKm` · `totalKm` · `totalMoveMin`에도 왕복이 포함된다. **체력 합의가 숙소 왕복을 빼고 계산되던 문제가 사라진다.**

실제 출력 예시 (난바 2박 → 우메다 2박):

```
1일차 난바 호텔 · 출발 0.2km · 복귀 0.6km · 하루 걷기 2.2km
2일차 난바 호텔 · 출발 5.7km · 복귀 0.1km · 하루 걷기 3.7km
3일차 우메다 호텔 · 출발 4.4km · 복귀 10.9km · 하루 걷기 3.0km
4일차 우메다 호텔 · 출발 1.7km · 복귀 4.3km · 하루 걷기 2.8km
```

3일차 복귀 10.9km처럼 **숙소를 옮기는 날의 부담이 숫자로 드러난다.** 전에는 보이지 않던 값이다.

### 3.2 참여자마다 숙소가 다를 때

**가장 많은 사람이 적은 숙소**를 그날 기준으로 삼고, 갈린 사실을 `conflicts`로 함께 돌려준다. 화면에서 확인을 받는 용도다.

중간 지점을 임의로 만들지 않는다. 같이 자는 숙소가 여러 개라는 것은 보통 입력 실수이고, 아니라면 사람이 정할 문제다.

### 3.3 주소 → 좌표

엔진은 **좌표를 받는다.** 주소 문자열을 좌표로 바꾸는 일(Google Places / Nominatim)은 서버에서 먼저 처리해 보내는 것으로 본다. 엔진이 외부 API를 부르면 계산이 네트워크에 묶이고, 같은 입력에 같은 결과가 나온다는 보장도 깨진다.

좌표 없이 들어오면 입력 오류로 돌려준다.

`run.mjs`가 계산 전에 거른다. 하나라도 걸리면 계산하지 않고 이유를 돌려준다.

```json
{"error":"invalid_input","issues":[{"field":"submissions[0].musts","message":"알 수 없는 장소: 없는곳"}]}
```

| 검사 | 내용 |
| --- | --- |
| 장소 id | 카탈로그에 없는 id |
| 꼭·제외 충돌 | 한 사람이 같은 곳을 양쪽에 넣음 |
| 트레이드오프 | 0~1 밖의 값 |

## 6. 팀에서 정해야 할 것

1. **`spend`를 평균으로 합치는 것** — 하한으로 바꾸면 아끼고 싶은 한 사람이 전체를 정하게 된다. 지금은 평균이지만, 돈 문제라 원리 3의 '숙소는 하한' 쪽에 가깝다고 보면 바꿀 수 있다.
2. **숙소가 갈릴 때 다수결** — 2:1로 갈리면 1명이 매일 더 멀리 다니게 된다. 다수결 대신 "각자 자기 숙소 기준으로 거리를 따로 보여준다"도 가능하다. 화면이 복잡해지는 대신 정확하다.
3. **1순위를 예산 밖에서도 넣는 것** — 원리 2를 지키려면 필요하지만, 1순위가 비싼 곳들뿐이면 예산 상한을 넘을 수 있다. 지금은 넘는 것을 허용하고 그 사실이 만족도에 반영된다.
