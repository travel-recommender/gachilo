# 논문 참고사항 정리

> 참고 논문: 김지우 외, "하이브리드 필터링과 동적 가중치를 적용한 상황 인식 기반 대화형 관광지 추천 시스템", 정보처리학회 논문지 제15권 제7호 (2026.7)
>
> 추천 점수를 계산하는 방식, 콜드스타트 처리, 근거를 LLM으로 다듬는 방법 등에서 겹치는 부분이 있어 그 부분 위주로 정리했습니다.

## 1. 두 프로젝트 비교

| | 논문 (관광지 추천 챗봇) | 우리 프로젝트 (여행 일정 합의) |
|---|---|---|
| 목표 | 개인 관광객에게 대화로 장소 추천 | 그룹 참여자 전원의 비공개 제약을 반영해 일정 확정 |
| 입력 | 대화 발화, 동반인/목적 속성 | 예산, 체력, 선호 장소, 거부 장소 (비공개) |
| 핵심 문제 | 콜드스타트, 환각(hallucination) | 형평성, 프라이버시(취향을 말할 수 없음) |
| 점수 산출 | 장기 선호도 + 실시간 맥락 3요소 가중합 | 개인 효용 → 그룹 취합 전략(평균/최소불만/공정성) |

## 2. 참고할 만한 아이디어

### 2.1 데이터가 부족할 때 상위 그룹 값으로 보정하기 (콜드스타트 처리)

논문은 특정 (동반인×목적) 조합의 리뷰 데이터가 부족하면, 더 상위 계층(목적 그룹 → 전체 평균)의 평점을 신뢰도에 비례해 섞어주는 계층적 보정 방식을 씁니다. 데이터가 많을수록 세부 그룹 값을 신뢰하고, 적을수록 상위 평균 쪽으로 값을 당기는 방식입니다.

**우리 프로젝트에 적용해볼 지점**: 개인 효용을 계산할 때, 사용자가 직접 고르지 않은 장소는 `카테고리 취향 × 0.42 + 장소 매력도 × 0.38` 고정 가중치를 쓰고 있습니다. 지금은 문제 없지만, 나중에 카테고리 세분화(예: "음식점 > 라멘")처럼 계층이 깊어지면, 하위 카테고리 데이터가 희박할 때 상위 카테고리 값으로 자연스럽게 보정하는 방식을 참고할 수 있습니다. 지금 당장 구현 우선순위는 낮지만, "알려진 한계"에 있는 "만족도 가중치는 임의 설정값" 문제를 풀 때 참고 후보로 적어둘 만합니다.

### 2.2 상황에 따라 가중치를 동적으로 바꾸는 구조

논문의 최종 점수는 4개 요소(장기 선호, 분위기 연속성, 거리, 키워드)의 가중합인데, 대화가 "탐색 초반"인지 "이어지는 추천"인지, 위치/키워드가 명시됐는지에 따라 8가지 시나리오별로 가중치 비율표를 따로 정의해 둡니다. 예를 들어 대화 초반엔 장기 선호 비중을 1.0으로 두고, 위치·키워드가 나오면 그 비중을 낮추고 거리·키워드 비중을 올립니다. (실시간으로 대화하면서 가중치 달라지는 느낌)

**우리 프로젝트에 적용해볼 지점**: 지금 3가지 취합 전략(평균/최소 불만/공정성)은 그룹당 하나로 고정해서 쓰고 있습니다. 깃허브 코드 설명 중 검증 결과에서 H1·H2는 지지되지 않았다는 결론이 나왔는데, 그럼 전략에 차이가 없었다는 게 됩니다. 어떤 전략을 쓸지는 별로 중요하지 않다는 건데... 그래서 논문처럼 "상황(단계)에 따라 방식을 다르게 쓴다"는 아이디어 자체는 살릴 수 있는데, 우리한텐 "대화 단계"가 없으니까 대신 **"일정에서 뭘 정하는 단계인지"**에 적용해보는 것도 괜찮을 것 같습니다:

코어 장소(모두가 같이 가는 필수 장소)를 정할 때 → 공정성 전략 사용 (아무도 소외 안 되게)
옵션 장소(가고 싶은 사람만 부분적으로 같이 가는 장소)를 정할 때 → 개인 효용 비중을 더 크게 (원하는 사람 취향을 더 반영)

즉, 지금처럼 그룹 전체에 전략 하나를 통일해서 쓰는 대신, "코어를 정할 때"와 "옵션을 정할 때" 서로 다른 계산 방식을 쓰자는 겁니다.


### 2.3 근거를 LLM에 넘길 때 쓸 프롬프트 구조 (가장 직접적으로 참고할 부분)


> "실제 서비스에서는 이 구조화된 근거를 LLM에 넘겨 자연스럽게 다듬을 예정이며, 현재는 LLM 없이 검증 가능하도록 규칙 기반으로 구현했다."

저희 README에 이렇게 써있는데, 논문에 정확히 이 단계를 이미 구현해놓은 것 같습니다. 논문의 Algorithm 1과 Table 4에서 쓰는 패턴은:

1. **System Role**을 명확히 지정 ("당신은 전문 여행 가이드다")
2. **Input**을 구조화된 필드로 명시 (리뷰 텍스트, 키워드 등)
3. **Output 포맷을 JSON으로 강제** (`{"Companion": "...", "Purpose": "..."}` 처럼 스키마와 선택지를 명시)
4. **Few-shot 예시**를 1~2개 붙여서 모호한 입력에서도 일관된 출력이 나오게 함 (현희 교수님 컴네 강의랑 비슷한 것 같음)
5. 사용자 의도(Intent)별로 프롬프트 분기 (추천/선택/상세정보/기타 등)

**우리 프로젝트에 적용해볼 지점**: LLM 연동으로 확장할 때, 지금 규칙 기반으로 만든 근거 데이터(코어/옵션 분리 이유, 만족도 구성 요소, 예산·체력 여유 등)를 그대로 위 구조의 **Input**으로 넣고, System Role을 "그룹 여행 일정의 근거를 설명하는 가이드"로 잡은 뒤, Output을 자연어 문장 1~3개로 제한하는 식으로 그대로 응용할 수 있습니다. 특히 "Few-shot 예시로 모호한 입력도 일관되게 라벨링"하는 부분은, 우리처럼 "왜 이 장소가 옵션으로 빠졌는지"처럼 케이스가 여러 갈래인 설명에 유용할 것 같습니다.

### 2.4 RAG로 환각을 막는 방식 → 우리는 "근거 데이터 강제 주입"으로 대응 가능

논문에서는 LLM이 사실이 아닌 정보(영업시간, 위치 등)를 지어내는 걸 막기 위해, 답변 생성 시 미리 구축한 지식 베이스에서 검색한 데이터만 근거로 쓰게 강제합니다(RAG). 성능 평가에서 환각률이 Vanilla 모델 3.76% → 제안 모델 1% 미만으로 줄었다는 결과도 있습니다.

**우리 프로젝트에 적용해볼 지점**: 우리는 검색엔진 기반 RAG까지 구축할 필요는 없을 것 같습니다.. 대신 이미 계산해 둔 구조화된 근거(예산 여유율, 꼭 반영 여부, 이동거리 등 숫자 데이터)를 LLM 프롬프트에 그대로 텍스트로 넣고, "이 숫자 외의 정보는 지어내지 말 것"이라는 제약을 프롬프트에 명시하면 사실상 같은 효과를 얻을 수 있습니다. 즉 우리 시스템은 이미 신뢰할 수 있는 근거를 규칙으로 만들어두었기 때문에, 논문처럼 별도 검색 인프라 없이도 환각 방지가 비교적 쉬운 구조라는 점을 PR에서 강조할 만합니다.

### 2.5 가상 사용자 시뮬레이션 평가 방식

논문은 GPT-4o로 100개의 영문 시나리오를 만들고, 가상 AI 사용자가 시스템과 자동으로 대화하게 한 뒤, 성공률(SR@K)·NDCG·평균 턴 수·환각률 4가지 지표로 평가합니다.

**우리 프로젝트에 적용해볼 지점**: 우리도 이미 가상 그룹 500개를 돌릴 거라서 이 아이디어 자체는 이미 있는 셈입니다. 근데 논문처럼 **지표를 다각화**하는 부분은 참고할 만합니다. 지금은 평균 만족도·최저 만족도·편차 위주인데, 논문의 "성공률(예: 만족도 임계값 이상을 달성한 비율)"이나 "코어 구성이 바뀐 비율" 같은 지표를 좀 더 체계적으로 나눠서 보여주는 방식을 벤치마킹할 수 있습니다.
