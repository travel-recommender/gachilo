# 150곳 확정 데이터 시뮬레이션 — 7주차

> 7주차 체크리스트 1·2·3 산출물
> 데이터: `오사카_장소데이터_최종통합_20261014.xlsx` 150행 → 일정에 쓸 수 있는 **139곳** 사용 (`scripts/sim150/places150.json`)
> 코드: `backend/engine/consensus.ts` (수정 없이 그대로 실행)
> 스크립트: `scripts/sim150/` 의 `sim.mjs` · `sim2.mjs` · `sim4.mjs` · `sim6.mjs` · `sim7.mjs`

조건: 300개 그룹 · 3~5인 · 1인당 5곳 찜 + 1곳 거부 · 2박3일 · 고정 시드(20261014)

- 139곳 실행에는 **데모 36곳을 섞지 않는다**(`PLACES`를 비운다). 36곳 실행은 데모 36곳만 쓴다.
- `places150.json`의 `cost`는 **엔화**라 **1엔=9.5원(가정값)** 으로 환산해 넣는다. 비용이 빈 곳은 15,000원으로 가정한다.
- 모든 장소의 `popularity`는 0.5로 고정한다(4.3 참고).

### 다시 돌려보는 법

```sh
# 저장소 루트에서 (Node 24)
node scripts/sim150/sim.mjs     # 1번 표 — 전략별 결과가 갈리는지
node scripts/sim150/sim2.mjs    # 2번 표 — 전략끼리 짝지어 비교
node scripts/sim150/sim6.mjs    # 2.1 표 — 관문별 통과율
node scripts/sim150/sim7.mjs    # 2.3 표 — 관문 수정안 검증 (원본은 안 건드리고 임시 폴더 사본에 패치)
node scripts/sim150/sim4.mjs    # 3번 표 — 조건별 스윕
# Node 22라면 node --experimental-strip-types ...
```

### 이 시뮬레이션이 다루는 범위

이 문서의 숫자는 모두 **`consensus.ts`(합의 엔진)에 139곳을 넣은 결과**다.
지금 150곳 방에서 보이는 결과(`backend/engine/real.mjs`)와 같은 엔진의 결과가 아니다.
`real.mjs`는 현재 전략을 적용하지 않는다 — `strategy: 'average'` 고정,
"꼭 가기 → 찜한 사람 수 → ID" 순서로 고른 곳만 배치한다(`backend/README.md` 2026-09-30 절, PR #29/#30).
시연 근거로 쓸 때는 "consensus.ts에 139곳을 넣은 결과"라고 같이 밝힌다. 실제 경로에 전략을 붙이는 일은 #3의 10-c다.

## 2. 찾은 문제 — 전략이 이름값을 못 한다

전략이 갈린 228개 그룹만 골라 **같은 그룹 안에서** 전략끼리 짝지어 비교했다.

| 가설 | 평균 차이 | t | 이긴 비율 |
| --- | ---: | ---: | ---: |
| least_misery가 최저 멤버 만족도를 올리나 | +0.0007 | 0.42 | 89/228 (39%) |
| average가 전체 평균을 올리나 | +0.0003 | 0.51 | 114/228 (50%) |
| fairness가 불평등(지니)을 낮추나 | +0.0002 | 0.53 | 68/228 (30%) |

**셋 다 자기 이름대로 동작한다고 볼 수 없다.** 차이가 모두 우연 수준(|t| < 2)이다.

### 2.1 원인 하나 — 고정 임계값 `score < 0.3`

`consensus.ts:312`에 AI 채움(아무도 안 고른 곳으로 빈자리 채우기) 관문이 있다.

```ts
if (score < 0.3) continue;
```

그런데 `score`는 전략마다 **축이 다르다.**

```
average      = 평균(효용)
least_misery = 최솟값×0.8 + 평균×0.2     ← 구조적으로 평균보다 낮음
fairness     = 평균 − 0.7×표준편차        ← 구조적으로 평균보다 낮음
```

같은 0.3을 들이대니 전략마다 다른 비율로 잘린다. 139곳 × 300그룹 실측:

| 전략 | 점수 평균 | 최저효용<0.2로 탈락 | **점수<0.3으로 탈락** | 통과 |
| --- | ---: | ---: | ---: | ---: |
| average | 0.342 | 2.8% | **29.5%** | 67.7% |
| least_misery | 0.277 | 2.8% | **83.3%** | 13.9% |
| fairness | 0.281 | 2.8% | **70.8%** | 26.4% |

최저효용 관문(2.8%)은 전략과 무관하게 같다. 효용은 전략 이전에 계산되기 때문이다. **차이는 전부 점수 관문에서 난다.**

### 2.2 그래서 무슨 일이 생기나

AI 채움이 많이 일어나는 조건(찜 2곳 · 5박 · 후보 30곳)에서 least_misery는 통과하는 장소가 적으니 **코어가 작아진다.**

```
코어 크기   average 17.6곳 · least_misery 7.6곳 · fairness 11.3곳   (자리 18)
```

만족도 계산(`satisfactionOf`)에서 예산·체력은 `0.55 + 사용률×0.45`라, 한도 안에서는 **쓸수록 올라간다.** 코어가 작으면 예산·시간을 덜 쓰게 되고 만족도가 내려간다.
이 조건에서 least_misery는 최저 멤버를 **−0.0237 (t −33.7)** 낮춘다.

### 2.3 관문 수정안 — 이것만으로는 부족하다

관문을 전략과 무관한 양(평균 효용)으로 바꾸는 안을 사본에 적용해 같은 시드로 다시 돌렸다.

```ts
// 현재
if (score < 0.3) continue;

// 수정안
if (subs.map((s) => utilityOf(place, s)).reduce((a, b) => a + b, 0) / subs.length < 0.3) continue;
```

| | 현재 | 수정안 |
| --- | --- | --- |
| 코어 크기 | 17.6 / 7.6 / 11.3곳 | 18.0 / 18.0 / 18.0곳 |
| least_misery가 최저멤버를 올리나 | −0.0237 (t −33.7) ✗ | −0.0010 (t −3.0) ✗ |
| fairness가 지니를 낮추나 | +0.0004 (t 2.9) ✗ | +0.0001 (t 2.7) ✗ |

코어 크기는 맞춰지고 least_misery의 손해도 크게 줄지만, **방향은 여전히 반대다.**
관문 말고도 AI 채움 단계에서 least_misery가 최저 멤버를 챙기지 못하는 원인이 더 있다. 관문 수정 PR은 이 원인을 더 찾은 뒤에 올린다.

> 처음 올린 버전에는 수정안이 "+0.0022 (t +6.2) ✓ 맞는 방향"이라고 적혀 있었다. 139곳 실행에 데모 36곳이 섞여 있었기 때문이고(아래 6번), 섞이지 않게 고치니 위와 같이 바뀌었다.

찜한 곳끼리 순서를 정하는 단계(AI 채움 이전)에서 least_misery가 최저 멤버를 챙기지 못하는 문제는 #3의 13번 수정 PR에서 따로 다룬다.

## 3. 시뮬레이션 조건에 대한 주의

기본 조건(찜 5곳·2박3일)에서는 **코어 9곳이 거의 전부 누군가 찜한 곳**이었다. 3~5인 × 5곳 = 15~25곳인데 139곳 중에서 뽑으니 거의 안 겹쳐서, 자리(9)보다 찜이 대부분 많았다. 이러면 전략이 "찜 안 한 곳 중에 뭘 넣을까"를 결정할 일이 거의 없다(300그룹 × 3전략에서 AI 채움 17곳).

조건을 바꿔 확인했다.

| 조건 | 갈린 그룹 | 코어 구성 | least_misery 최저멤버 |
| --- | ---: | --- | --- |
| 찜5 · 2박 · 후보 139곳 | 226/300 | 9.0곳 중 8.9곳이 찜 | −0.0009 (t −0.5) |
| 찜5 · 2박 · 후보 20곳 | 159/300 | 8.9곳 중 8.8곳이 찜 | −0.0002 (t −0.6) |
| 찜5 · 2박 · 후보 12곳 | 112/300 | 9.0곳 중 7.2곳이 찜 | −0.0022 (t −4.9) |
| 찜3 · 2박 | 150/300 | 9.0곳 중 8.7곳이 찜 | −0.0006 (t −2.0) |
| 찜2 · 2박 | 203/300 | 8.9곳 중 6.9곳이 찜 | −0.0076 (t −16.8) |
| 찜5 · 5박 | 196/300 | 17.8곳 중 16.0곳이 찜 | −0.0015 (t −5.6) |
| 찜2 · 5박 · 후보 30곳 | 277/300 | 17.6곳 중 6.7곳이 찜 | −0.0237 (t −33.7) |

**AI 채움이 많을수록(찜이 자리보다 적을수록) least_misery의 역효과가 커진다.** 기본 조건에서 티가 안 났던 이유다. 실제 서비스에서는 사용자가 공통 롱리스트에서 고르므로 찜이 더 겹치고, 그러면 빈자리가 생겨 이 경로를 타게 된다.

14주차 가설 검정 때 **찜 개수와 후보 풀 크기를 조건으로 함께 보고해야 한다.** 이 둘에 따라 결과가 크게 달라진다.

## 4. 데이터 쪽 기록

### 4.1 139/150곳만 쓴 이유

엑셀 원본(20261014)으로 다시 확인한 제외 사유:

| 곳 수 | 사유 | 예 |
| ---: | --- | --- |
| 9 | `record_status` = "제외" (폐업 표시·실재 미확인 등) | 리온 카페, 아즈안, 보빈, 게마 갑문 |
| 1 | `category` 빈칸 (보류·카테고리 미확정) | 헬로 라이프 |
| 1 | `category` = "복합문화" — 시뮬레이션 카테고리 변환표에 없음 | 덴시바 이나 |

나머지 139곳은 엑셀과 `places150.json`을 필드별로 대조해 이름·카테고리·좌표·비용·체류시간·짐·실내 여부가 모두 같음을 확인했다.
(처음에는 "카테고리 또는 좌표가 비어 제외"라고 적었으나, 엑셀로 대조해 보니 위와 같아 고쳤다.)

이 엑셀(10/14)은 서버가 쓰는 `osaka_places_150_fresh.json`(9/23 수집, 10/6 커밋)보다 새것이다. 분류(체험·오락, 복합문화)와 이름 7곳이 다르다.

### 4.2 빈 필드와 단위

| 필드 | 채워짐 | 영향 |
| --- | ---: | --- |
| `cost` | 65/150 (43%) | **엔화**. 1엔=9.5원(가정값)으로 환산했다. 비는 곳은 15,000원으로 가정했다. 예산 제약이 실제보다 느슨하거나 빡빡해질 수 있다 |
| `covered` | 99/150 (66%) | 10주차 날씨 분기에서 쓸 값. 지금 계산에는 영향 없음 |
| `opening_hours` | 141/150 | 문자열이라 파싱 전. 지금은 전부 09:00~21:00으로 두고 돌렸다 |
| `area` | 147/150 | 구 단위(大阪市北区 등) 15개. 날짜별 묶기에 쓰기엔 거칠다 |

`stay_min`은 150/150 채워져 있으나 값이 6종(30·50·60·90·120·180)뿐이고, 카페 21곳은 전부 60분, 자연 19곳은 전부 120분이다. 장소를 구분하는 용도로는 쓰기 어렵다.

환율 9.5는 `backend/README.md`의 테스트 예시와 같은 값이다. 서버의 `cost_krw`는 운영자가 설정한 하나은행 고시환율을 쓰므로, 1인 비용 같은 금액 지표는 참고로만 본다.

### 4.3 `popularity`

현재 `Place` 타입에 `popularity` 필드가 있고 효용 계산에 쓰이는데, **150곳 데이터에는 이 값이 없다.** 36곳 `places.ts`에 들어 있는 값은 수집 데이터가 아니라 프로토타입 작성 시 손으로 넣은 값이다.

이번 시뮬레이션은 모든 장소(36곳 실행의 데모 장소 포함)에 `0.5`를 넣고 돌렸다. 수식에서 항을 빼는 것과 같다.

별도 검토가 필요한 사항이라 **다음 PR에서 따로 다룬다.**

## 6. 리뷰 반영 기록 (PR #50, 2026-10-19)

혜인 리뷰로 찾은 문제와 고친 내용. 숫자는 모두 고친 스크립트로 다시 뽑았다.

| 문제 | 영향 | 고친 방법 |
| --- | --- | --- |
| `allPlaces()`가 `[...PLACES, ...CUSTOM]`이라 139곳 실행의 AI 채움 후보에 **데모 36곳이 섞임** (데모 장소는 원래 popularity 그대로) | 관문 수정안 검증(2.3)이 ✓에서 ✗로 바뀜. sim4·sim6 숫자도 바뀜. 1번 표(찜5·2박)는 AI 채움이 거의 없어 거의 그대로 | 139곳 실행 전에 `PLACES.length = 0` |
| 36곳 실행이 `setCustomPlaces(36곳)`이라 **36곳이 두 번** 들어감 | 기준선 52.0% → 52.7% | 36곳 실행은 `setCustomPlaces([])`, 데모 원본의 popularity를 0.5로 고정 |
| `cost`가 **엔화**인데 원화 엔진에 그대로 넣음 | 예산 제약이 거의 안 걸림. 77.7% → 76.0% | 1엔=9.5원으로 환산 |

`sim.mjs`는 확인용으로 "AI가 채운 코어 수"와 "코어에 같은 id가 두 번 든 결과 수"를 함께 출력한다.
