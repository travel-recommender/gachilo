# 오사카 지점별 추가 수집 (2026-10-19)

쇼핑·음식·프리쿠라 **58건**의 출처와 지점별 차이를 공유한다. 신규 후보 55건,
기존 장소 보완 제안 3건이며, 별도 보류 2건은 신규 후보 수에 포함하지 않는다.
브랜드마다 하나로 합치지 않고 **실제 지점마다 한 행**으로 관리한다. 150곳은 상한이 아니다.

이 PR을 병합하면 수집 자료와 가져오기 도구를 팀이 사용할 수 있다.
**앱에서 선택하거나 일정에 배치할 장소를 자동으로 늘리는 PR은 아니다.**
현재 추가 후보에는 입구·좌표·이용 공간·체류 기준과 방문일별 운영 규칙 검증이 남아 있다.

## 파일과 확인 상태

| 파일 | 용도 |
| --- | --- |
| `branches.json` | 지점별 수집 원장. 도구가 읽는 정본. 출처 종류·URL·확인일·가격 조건·검색 표기·남은 확인 사항 포함 |
| `collection.xlsx` | 동일한 58건의 사람이 읽고 작성하는 스냅샷. 기존 중복·보류 탭 및 연노랑 추가 입력칸 포함 |

JSON과 Excel은 자동으로 양방향 동기화하지 않는다. Excel을 보완해서 전달한 경우
`collection_id`로 원장과 대조하고, 확인한 값·출처·날짜만 원장에 옮긴 뒤 검사한다.
지도 API 키, 계정 정보, 리뷰 본문·사진은 포함하지 않는다. 유료 API 호출도 없다.

- 쇼핑 41 / 음식 관련 15 / 프리쿠라 2. 음식에는 식당 후보 12, 포장 구매 1, 타코야키 간식 2가 있다.
- 공식 매장 사이트, 쇼핑몰 운영사, 상점가 공식 목록 출처를 `source_kind`로 구분한다.
- `reference_cost_jpy`는 조건부 메뉴/이용료 참고값이다. 모든 지점의 확정 예산이 아니다.
  쇼핑 입장료와 구매 예산을 합치지 않으며 미확인 금액은 `null`이다.
- 표시 이름·권역·카테고리·검색 표기는 작업 분류다. `체험·오락`은 PR #44와 연결을 확인해야 하며,
  이 파일을 추가하는 것만으로 현재 main의 API/엔진 분류 계약이 바뀌지 않는다.
- 같은 건물 안의 백화점과 입점 브랜드는 독립 방문 대상일 수 있다. 층·입구를 검증하고
  시설 관계를 정한 뒤 중복 이동·체류 계산을 막아야 한다. 주소가 같다는 이유만으로 합치지 않는다.
- 551 포장점과 와나카 간식점을 자동으로 점심·저녁 한 끼로 세지 않는다.

## 검토본 만들기

저장소 루트에서 Python 3.10 이상으로 실행한다. 출력 폴더는 **존재하지 않는 새 폴더**로 지정한다.

```sh
python3 scripts/import_branch_collection.py --output-dir /tmp/gachilo-branch-review
```

현재 main의 150개 정본을 읽어 신규 후보 55개를 더한 **205개 검토본**을 만든다.
기존 정본 파일, API의 기본 데이터 경로, 실행 중인 DB는 변경하지 않는다.
현재 main에 아직 반영되지 않은 사용자 로컬 최종 CSV를 대신 통합했다고 보지 않는다.

| 출력 | 내용 |
| --- | --- |
| `places.review.json` | 기존 `place / field_sources / source / review` 형식의 검토본. 기존 150개 기록 그대로 + 신규 55개 |
| `updates.review.json` | 기존 장소 3건의 현재 값과 제안, 보류 2건. 자동 덮어쓰기 없음 |
| `summary.json` | 입력 해시, 추가/중복/보완 수, 미승격 상태 |

기존 보완 대상은 `osaka_026`(이치란 도톤보리 별관), `osaka_022`(다이마루 신사이바시),
`osaka_draft_f1ba0aa6ab58`(한큐 우메다)다. 같은 브랜드의 다른 지점으로 바꾸지 않는다.
보류 중인 이치란 본관 `osm_node_2546559085`는 별관과 합치지 않는다.
라파 오사카는 공식 검색 결과의 폐점 안내와 원문 재접속 실패 범위를 원장에 명시했다.

다른 기준 JSON을 쓸 때는 `--base 경로`를 지정한다. 기존 장소 ID가 없거나 중복되면 실패한다.
이미 만든 검토본을 기준으로 같은 원장을 다시 읽으면 동일 후보는 중복 추가하지 않는다.
같은 ID의 내용이 다르면 중단하므로 사람의 수정 사항을 덮어쓰지 않는다.
`branch_...` ID는 검토 중에도 유지한다. 지점 이름 수정이나 정렬만으로 다시 발급하지 않는다.

## 서비스 데이터 반영까지 남은 단계

1. 실제 입구·좌표, 주요 이용 공간, 기준 메뉴의 세금/수량/시간 조건을 출처와 함께 확인한다.
2. 체류시간·짐 증가량의 팀 기준, 포장/간식의 방문 역할, 시설 내부 중복 처리를 정한다.
3. 자연어 영업시간을 방문일별 운영 규칙으로 검토한다. 휴무·주문 마감·예외일과 심야 시간을 포함한다.
4. 기존 보완 3건을 별도 변경 원장으로 대조한다. 현 정본의 값·출처·이력을 보존한다.
5. 검증한 후보만 정본과 일정용 프로필에 반영하는 후속 PR에서 실제 일정 검사를 통과시킨다.
   화면/서버/엔진의 실제 장소 연결(이슈 #3의 10-a/10-b/10-c)과 목록 개수 제한도 함께 확인한다.

가져오기 도구는 **승격 도구가 아니다.** 참고 가격이나 사용자가 입력한 체류시간이 있어도
자동으로 `cost`, `covered`, `stay_min`, 좌표, `bag_load`를 확정하지 않는다.
원래 값은 `review.branch_collection`에 모두 보존하고 신규 후보의 `schedule_ready=false`와
`branch_collection_review_required` 차단 사유를 유지한다. source를 OSM으로 위장하지 않는다.
출력 JSON을 현재 API 기본 경로에 복사해서 이 단계를 우회하지 않는다.

## 검사

```sh
python3 -m unittest discover -s scripts -p test_branch_collection.py -v
node --test scripts/test_branch_collection.mjs
```

첫 검사는 기존 기록 보존, 재실행 중복 방지, 잘못된 ID/출처/날짜/숫자 거부,
원본/출력 덮어쓰기 방지와 150개 상한 부재를 확인한다. 두 번째 검사는 Node 24 이상에서
기존 실제 일정 검증기가 55개 후보를 읽을 수 있고 일정 사용은 계속 차단하는지 확인한다.
